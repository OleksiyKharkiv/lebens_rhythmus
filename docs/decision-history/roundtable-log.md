# Roundtable Log — Lebens Rhythmus

"Рыцари круглого стола" — формат по образцу `numi/docs/decision-history/roundtable-log.md`.

**Правила:** Enthusiast-Adventurer — 2 голоса (двигатель прогресса, максималист).
Внешние эксперты спорят pro/con из своей области, канализируя их
публично известную инженерную/дизайнерскую/бизнес-философию — **не
выдуманные цитаты, не буквальные высказывания реальных людей**, та же
конвенция, что и в numi Roundtable #4. Tech Lead синтезирует и
финализирует. Лог хранится не как решение, а как ответ на вопрос "почему
мы решили X" — через месяцы, когда контекст забудется.

**Дистиллированные решения (ADR) — не здесь, а в
[`docs/architecture/decisions.md`](../architecture/decisions.md).** Этот
файл — полный нарратив, тот в свою очередь — сухой остаток.

### Phase 0 — Брифинг: LR на 20.07.2026

Java 21 / Spring Boot 3.5.7 / Gradle, PostgreSQL 16, Spring Security + JWT
(HS256), статический MPA-фронтенд без фреймворка (18 страниц), k3s на
домашнем сервере, GitLab CI, Cloudflare Tunnel (`cf_worker_lr.js` —
неиспользуемый артефакт, подтверждено владельцем: реальный путь трафика
через CF Tunnel, не через Worker).

Архитектура — слоистая (controller→service→repository→entity), задумана
гексагональной, по факту нет: JPA прошита прямо в domain-классы, портов
для внешних систем нет, потому что внешних систем нет вообще. БД без
миграций (`ddl-auto=update` + runtime ALTER-костыль), без бэкапов, без
HA. Безопасность: JWT_SECRET plaintext в Helm при том, что DB-пароль
защищён правильно; один контроллер без `@PreAuthorize`; хеширование
пароля дважды почти ломалось за 7 месяцев. Фронтенд: мультиязычность
(DE/EN/UA) уже в БД (`Activity`, `Group`), нигде не используется.

Бизнес-контекст: разрыв "нет платежей" породил отдельный проект (Numi) —
интеграция LR↔Numi решена только на уровне идеи.

Продуктовый wishlist от Olena (неприоритизированный): презентационный
сайт с топ-UI/UX и видео; регистрация + личный кабинет с дневником и
напоминалками; дашборд админа-режиссёра; оплата (Numi + Stripe +
другие); AI-промо в соцсетях/WhatsApp/Telegram; "всё для ERM, что не
описано"; рекомендации по must-have для PWA.

### Phase 1 — Вопросы панели (полный текст сохранён построчно — 17

  схемы/ORM; кто владелец правды о расписании.
- **Gosling/Johnson/Goetz** — состав команды (соло + AI); принципиальность

  на AI-IDE автосгенерированный хардкод); готовность инвестировать в
  качество vs скорость.
- **Harris/Osmani/Norman** — кто поддерживает фронтенд после старта; кому
  верить в выборе Svelte; целевые устройства по производительности;
  портрет пользователя личного кабинета; референсы стиля.
- **Hightower/Vogels/Russinovich** — реалистичный рост нагрузки за год;
  psychological status `lr-dev` (dev или уже прод); ценность текущих
  данных; твёрдость даты инфра-апгрейда; кто имеет доступ к кластеру.
- **Hunt/Schneier** — сколько реальных пользовательских данных сейчас;

### Phase 2 — Рекомендации must-have / по максимуму (п.4.7)

**Enthusiast (2 голоса):** минимум — настоящий PWA (offline, "Add to Home
Screen"), Stripe для быстрых разовых оплат, мультиязычность DE/EN/UA
(фундамент уже есть), видео/фото-портфолио с согласия родителей. По
максимуму — AI-черновики постов в соцсети по факту занятия, WhatsApp-бот
"есть ли места", интеграция с Google/Apple Calendar.

**Контрголос (Kerstiens/Momjian/Vogels):** сначала данные не теряются →
авторизация не течёт → миграции версионируются → потом уже AI-эффекты.
Порядок, не отмена списка.

### Phase 3 — Предварительное видение v1 (черновик-гипотеза)

PWA с офлайном, DE/EN/UA, личный кабинет (форма зависит от ответа
Cagan), дашборд Olena, двойная оплата (Numi + Stripe), AI как инструмент
промо (не автономный бот), реальные миграции, реальные бэкапы,
JWT_SECRET через Secret, частичное отделение домена от JPA. Не решено:
фреймворк, масштаб команды, модель угроз, приоритет "одна главная вещь",
судьба Cloudflare Worker-файла, твёрдость даты инфра-апгрейда.

### Round 2 — ответы владельца + живое исследование UI

**Ответы на Phase 1 (дословный смысл сохранён):**

- **Мартину:** формальных инвариантов нет, только несовершенная
  ERM-диаграмма. Не все 17 сущностей нужно разделять — но нужна

- **Эвансу:** да, была мысль о преподавателях-субподрядчиках со своими
  курсами — усечённые права администратора == роль "Преподаватель" с
  возможностью создавать расписание и состав групп (по времени, по
  возрасту, по вместимости) и резервировать помещения в общем графике
  лаборатории. Формальной проверки/реализации пока нет, только задумка.
- **Гослингу:** команда — я один + Claude Code. Build-tool не
  принципиален (личная неприязнь к Maven POM.xml — вероятно, просто
  недостаточный опыт с ним, не объективная оценка).
- **Джонсону:** auth — "почти хардкод от AI-IDE", нужна глубокая ревизия
  и вероятна полная перестройка хеширования, с шифрованием чувствительных
  полей (персональные/банковские данные) по GoBD/DSGVO. Качество,
  надёжность, гибкость — высший приоритет, время инвестировать готов.
  Согласен на осознанное дублирование модулей, если это повышает
  гибкость/читаемость/модульность.
- **Гётцу:** "спешка, хорошая лишь при ловле блох" — нужно и
  проинспектировать модель, и поддержать миграцией.
- **Харрису:** старт — я + Claude, возможно фронтендер позже. Текущего
  фронтенда почти нет содержательно — весь под снос, держаться не за что.
- **Османи:** offline/PWA — очень хотелось бы, но не первый приоритет
  (тикет создаём). Целевая аудитория по устройствам — средний немец (уже
  "ниже среднего" по благосостоянию) + готовность "быстро ползать" на
  слабых индийских Android.
- **Норману:** пользователи — от подростков (регистрируют по закону
  родители) до буквально бабушек, оба конца спектра должны быть
  впечатлены. Референсов на конкретные сайты сознательно нет — ставка на
  непохожесть, полный собственный ресёрч фич, не копирование трендов.
- **Хайтауэру:** рост в этом году небольшой, со следующего года
  ожидается, целевой ориентир — 100 постоянных участников за год.
  `lr-dev` психологически уже прод.
- **Вогельсу:** текущие данные не имеют ценности — можно сносить и
  строить заново правильно. Дата инфра-апгрейда нетвёрдая, окно
  сентябрь-ноябрь.
- **Руссиновичу:** доступ к кластеру — только я.
- **Ханту:** реальных данных нет, только 3 тестовых аккаунта — все члены
  семьи.
- **Шнайеру:** реалистичный противник — первый и последний из
  предложенного списка: случайный бот-сканер портов **и** state-level
  actor. Не конкурент, не обиженный участник.
- **Момджиану:** данных мало — пересоздаём правильно, с миграциями.

**Живое исследование факта (не мнение):** живой браузер и WebFetch не
смогли достучаться до `tlab29.com` (403/таймаут — вероятно, Cloudflare),
поэтому UI изучен напрямую по реальному исходнику трёх страниц из этого
репозитория (`frontend/pages/{home/index,login/login,about/about}.html`,
`frontend/styles/main.css`):

- Главная страница — один экран: заголовок, подзаголовок, абзац, две
  кнопки. Ни программ, ни галереи, ни отзывов, ни видео.
- About — один блок, фоновая картинка `pyramid.jpg` (тематически не
  связана с театром), один абзац текста. Ни истории, ни лиц, ни команды.
- Ноль дизайн-системы: `main.css` не содержит ни одной CSS-переменной,
  единственное объявление шрифта — `font-family: sans-serif`.
- Баг: `lang="en"` на главной и About при полностью немецком тексте
  (только `login.html` помечен верно, `lang="de"`).
- "Passwort vergessen?" ведёт на `href="#"` — мёртвая ссылка, функции
  восстановления пароля нет ни на фронте, ни на бэке.
- Минимальная длина пароля в форме регистрации — 6 символов.
- Плюс найденный: форма регистрации корректно разносит два отдельных
  GDPR-чекбокса (AGB / Datenschutz) с реальными ссылками — единственный
  участок текущего UI, сделанный добросовестно.

**Ответы на оставшиеся вопросы (Cagan/Godin), плюс новый факт о залах:**

### Round 2 — реакции панели

- **Мартин:** конкретный кандидат на эталон domain/persistence-разделения
  — `Group`/`Workshop`, потому что именно туда бьёт роль "Преподаватель".
  Не браться за все 17 сразу.
- **Эванс:** субподрядчики-преподаватели — полноценный bounded context
  "Faculty Management", не косметика поверх роли `TEACHER`. Хорошая
  новость: в коде уже есть частичный скелет (роль `TEACHER` существует, с
  несколькими read-эндпоинтами по `teacherId`) — не с нуля. Про залы: в
  модели уже разделены `Event.venue_id` и `Workshop.venue_id` — точечная
  привязка зала к конкретному событию архитектурно уже заложена, не
  хватает UI, который это использует.
- **Джонсон:** "почти хардкод от AI-IDE" подтверждает асимметрию
  JWT_SECRET/DB-пароль, найденную в `ARCHITECTURE_OLD.md`. Field-level
  шифрование — через `AttributeConverter`/`@Convert` на уровне JPA-колонки
  или отдельный порт `EncryptionService` (граница — вопрос к Мартину).
  Владелец кластера один — снимает срочность "чужого доступа", не снимает
  вопрос качества.
- **Харрис:** "всё в утиль" упрощает работу — не нужно проектировать
  частичную миграцию 18 страниц, можно строить с нуля сразу под
  архитектуру компонентов.
- **Хайтауэр/Вогельс/Момджиан (синтез):** ~100 участников/год = почти
  нулевая инфра-нагрузка, данные не ценны — значит схему БД и миграции
  можно и нужно пересоздавать СЕЙЧАС, не дожидаясь осеннего апгрейда
  железа. Это две разные шкалы времени, которые ранее смешивались:
  схема/миграции — не привязаны к железу; HA/бэкапы/апгрейд — привязаны
  к окну сентябрь-ноябрь.
- **Хант/Шнайер (синтез):** 3 тестовых аккаунта = лучшее возможное окно
  для перестройки auth/шифрования, пока цена ошибки минимальна. Модель
  угроз (боты + state actor, не инсайдер/конкурент) — приоритет защите от
  automated scanning и криптогигиене выше, чем защите от инсайдерской
  угрозы.
- **Каган:** MVP-периметр от владельца буквально совпал с тремя
  страницами, только что изученными в реальном коде (Home + About +
  Login/Register) — хорошая конвергенция.
- **Годин:** корректирует предложение Enthusiast'а из Phase 2 — AI не
  заменяет Olena в соцсетях, а даёт ей лёгкие инструменты быстро
  делиться моментом.

  спектакли — "пока не думали", не блокирует ничего.
- Логотип есть, цвета — свободны.
- Контент после запуска — Olena сама, редко (пару раз в месяц) — не

### Часть 1 — Что произошло и почему это прозевали

**Moussouris:** Это не "забыли поставить аннотацию" — это решение о
зависимости, принятое без соответствующего threat model, на этапе
scaffolding, и никогда не пересмотренное. Характерно, что это
обнаружилось не при обычном код-ревью, а при первом целенаправленном
аудите именно поверхности атаки — потому что обычное ревью проверяет
код, который написали, а не то, что фреймворк молча включает сам.
Именно для таких вещей и существует практика bug bounty: внешняя
сторона, реально пробующая входные данные против живой поверхности, а
не читающая diff.

**Mackey:** Строка в `build.gradle` появилась практически день в день с
основанием бэкенда — классический артефакт из Spring Initializr или
скопированного стартера, не осознанное решение. Ни разу не
пересмотренная зависимость — это ровно то, для чего существует
SBOM/PBOM-практика: "что реально работает и почему" должен быть живым,
непрерывно проверяемым вопросом, не разовым выбором при scaffolding.
Полное дерево зависимостей (`./gradlew dependencies`) для этого проекта
запрашивалось за 9.5 месяцев ровно один раз — сейчас, в рамках LR-022.

**Wysopal:** Форма ошибки та же, что у уже закрытого в этой же сессии
LR-020 (Bean Validation без провайдера) — код, который синтаксически
корректен, выглядит как обычный Spring Boot проект, и никогда не был
проверен под реальным runtime-поведением. Неважно, попал ли чекбокс в
Spring Initializr от человека или от AI-ассистента — режим отказа
одинаковый. Две находки одной формы в одном проекте за одну сессию — это
не совпадение, это структурный пробел в процессе верификации, не два
independent glitches.

**Winch:** `SecurityConfig`'s `.anyRequest().authenticated()` отработал
ровно так, как спроектирован — как safety net, а не как замена
пообъектным решениям об авторизации. Реальный пробел: авто-
сгенерированные Spring Data REST контроллеры (`RepositoryEntityController`
и т.д.) никогда не проходили через реальную модель авторизации этого
приложения (`@PreAuthorize` на каждом хендрайтен-контроллере), потому
что команда даже не знала, что эта HTTP-достижимая поверхность
существует. Ревью "пройти по каждому контроллеру и проверить
`@PreAuthorize`" — именно то, что делал LR-006 и каждый последующий
Architecture Pre-Check в этой сессии — структурно не может поймать
такой класс бага, потому что проверяет написанный код, не реально
достижимую HTTP-поверхность целиком.

**Long:** Spring Data REST — легитимный, активно поддерживаемый проект,
спроектированный для другого сценария: быстрые CRUD-прототипы, где
экспозиция по умолчанию — это фича, а не баг, отключение —
осознанный opt-out (`@RepositoryRestResource(exported=false)`,
`disableDefaultExposure()`), не opt-in. Архитектура этого приложения —
deny-by-default решения по каждой бизнес-операции — несовместима с
opt-out-экспозицией по конструкции. Причина дыры — не дефект ни в одном
компоненте по отдельности, а архитектурное несоответствие между ними.

**Когда именно прозевали (сводка):** на этапе выбора зависимостей при
scaffolding (Oct 2025, до содержательного кода) → не поймано на
Roundtable #1 (архитектурный ребилд с явными местами "Безопасность",
Jul 2026 — нашёл LR-006, точечный `@PreAuthorize`-пробел, не полный
аудит зависимостей) → не поймано ни одним последующим Architecture
Pre-Check (проверяют diff против ADR/слоёв, не полную поверхность
зависимостей) → не поймано ни одним прогоном `architect-reviewer` (тоже
ревьюит diff, не build.gradle целиком, пока diff его не касается) →
поймано впервые целенаправленным DevSecOps-аудитом (LR-022), заведённым
именно потому что в этой же сессии дважды нашлось "код выглядит
защищённым, никогда реально не проверялся" (LR-014, LR-020).

**Возможные последствия неустранённой дыры:**

- Подтверждено вживую: любой зарегистрированный аккаунт → полный ADMIN
  одним запросом.
- Зависимость жила с первых недель проекта — значит дыра была
  теоретически эксплуатируема весь срок работы прода, не только с
  момента обнаружения.
- Полный дамп расшифрованных PII (включая, вероятно, контакты
  несовершеннолетних участников через `Participant`-репозиторий),
  bcrypt-хэши, взламываемые offline, все финансовые записи.
- DSGVO: ровно тот сценарий "неавторизованный доступ к персональным
  данным детей", который триггерит обязательное уведомление о breach —
  серьёзная юридическая, не только техническая экспозиция для студии,
  работающей с детьми.
- Цепная реакция: получив ADMIN, атакующий получает полную внутреннюю
  видимость и мог бы использовать её для поиска других дыр (например,
  уже найденных в этом же аудите LR-024 teacher IDOR, LR-030 Group
  mass-assignment) — одна дыра как плацдарм для нахождения следующих.

### Часть 2 — Почему именно этот фикс правильный

**Это не "новейшее решение" в смысле новизны паттерна** — это старый,
десятилетиями устоявшийся принцип (attack surface reduction / least
functionality, ядро NIST SSDF и OWASP ASVS), применённый корректно.
Что действительно современно: сам класс уязвимости (неаудированный
авто-экспозирующий компонент фреймворка рядом с рукописным API) стал
встречаться чаще именно из-за AI-ассистированного scaffolding (точка
Wysopal выше) — поэтому защита (минимализм зависимостей, системный
аудит зависимостей, SBOM в CI) получила свежую актуальность, хотя сам
принцип не новый.

**Winch/Long:** современная Spring Security-рекомендация (Spring
Security 6.x, которую проект уже использует) — явная, method-level
авторизация как основная защита, URL-паттерны в `SecurityFilterChain`
как более грубый второй слой. Архитектура этого приложения уже
полностью следует этой рекомендации везде, **кроме** случайно попавшей
Spring Data REST-поверхности, которая через эту модель вообще не
проходила. Фикс не вводит новый паттерн — он убирает единственный
компонент, нарушавший паттерн, которому всё остальное приложение уже и
так следовало правильно.

**Почему удаление, а не переконфигурация — архитектурно правильный
выбор:**

- Spring Boot's `@ConditionalOnClass`-автоконфигурация: без зависимости
  на classpath уязвимый код физически не существует в работающей JVM —
  не "отключен", а структурно отсутствует. Ни один property, ни один
  будущий конфиг-файл, ни один случайный bean override не могут его
  воскресить.
- Переконфигурация (`config.disableDefaultExposure()`) оставила бы
  живую, latent мину: зависимость всё ещё на classpath, всё ещё часть
  supply chain, в одном minor-апгрейде Spring Boot или одном
  непроверенном merge conflict от повторной тихой экспозиции всего.
  "Невозможно по конструкции" — строго более сильный инвариант
  безопасности, чем "отключено конфигурацией".
- Подтверждено grep'ом перед удалением: ни одна строка кода проекта не
  использовала реальное поведение Spring Data REST
  (`@RepositoryRestResource`/`RepositoryRestConfigurer`) — зависимость
  несла ноль пользы при 100% риска. Не компромисс, чистая асимметрия.

**Задействованные зависимости:**

- Убрано: `spring-boot-starter-data-rest` (и транзитивно — Spring
  HATEOAS-контроллеры, ALPS/profile metadata эндпоинты — всё ушло вместе
  с ним).
- Добавлено для этого конкретного фикса: ничего.
- **Зеркальный случай в этой же сессии:** LR-020 (`spring-boot-starter-
  validation`) — обратная сторона той же дисциплины. Там реальная фича
  (`@Valid`) была нужна, но провайдер отсутствовал — пришлось
  **добавить** правильную минимальную зависимость. LR-020 и LR-023
  вместе показывают одну и ту же дисциплину, применённую симметрично в
  обе стороны: зависимости должны точно соответствовать тому, что
  реально используется — добавлять то, что действительно нужно, даже
  если его не хватало годами; убирать то, что не нужно, даже если оно
  было с первого дня.

**Более широкий архитектурный принцип:** это тот же принцип минимальной
поверхности атаки, применённый на уровне зависимостей, который
согласуется со всем остальным, что уже верно в security-архитектуре
этого приложения — deny-by-default `.anyRequest().authenticated()`,
stateless JWT с fail-fast проверкой секрета, AES-256-GCM field-level
шифрование без небезопасного fallback'а, явный `@PreAuthorize` на
каждом хендрайтен-контроллере. Фикс не вводит новую архитектурную
опору — он убирает единственный компонент, который молча работал
**вне** архитектуры, которой всё остальное уже правильно следовало,
восстанавливая архитектурную согласованность, а не изобретая новую.

### Синтез (Tech Lead)

Корневая причина — не единичная ошибка, а структурный слепой пятно
процесса: каждый уровень ревью в этом проекте (Architecture Pre-Check,
architect-reviewer, даже Roundtable #1's явные security-места) по
конструкции проверяет **написанный код против архитектуры**, а не
**полную HTTP-достижимую поверхность против дерева зависимостей**. Это
не повод переписывать существующий процесс — точечные ревью diff'ов
корректны и должны оставаться, — а повод добавить недостающий, отдельный
класс проверки: периодический (не разовый) аудит "что реально на
classpath и зачем", тот самый, который LR-022 впервые провёл и который
стоит повторять не только при следующем большом security-инциденте.
Дешёвый CI-guard, предложенный `architect-reviewer` при ревью фикса
(grep/dependency-assertion, чтобы `spring-boot-starter-data-rest` не
вернулся незаметно), — минимальная версия этой институционализации,
пока не заведён отдельным тикетом.

### Исходные данные (факты, не мнение)

### Часть 1 — Что именно мониторить (не просто "включить Actuator")

**Long:** Spring Boot Actuator + Micrometer — идиоматичный, first-class
способ, не костыль поверх логов. У проекта уже есть `spring-boot-
starter-actuator` (используется для `/actuator/health`) — не хватает
`micrometer-registry-prometheus` (даёт `/actuator/prometheus` в формате,
который `otelcol-contrib`'s `prometheus`-receiver ожидает нативно, тот
же формат, что уже проверен для numi) и осознанного выбора, какие
кастомные метрики завести, а не просто "что Micrometer даёт из коробки".

**Winch:** авторизационные решения должны быть видимы как метрика, не
только как лог-строка — лог теряется, тренд на дашборде замечают.
`GlobalExceptionHandler` уже сегодня — единственная точка, через которую
проходят `AuthorizationDeniedException`/`AccessDeniedException`,
`BadCredentialsException`, аккаунт-локаут (после фикса LR-026) — это и
есть естественная, минимальная точка инструментации: один counter на
каждый уже существующий `@ExceptionHandler`, ничего не размазывается по
сервисам.

**Moussouris:** метрики должны отвечать не на "жив ли сервис", а на
"кто-то сейчас пробует то, что мы уже один раз закрыли" — то есть
каждая находка LR-022 должна получить свой сигнал, не абстрактный
"security dashboard".

Конкретный набор (обвязка вокруг уже существующих точек в коде, не
новая архитектура):

| Метрика | Откуда | Что показывает |
|---|---|---|
| `auth_login_failure_total{reason}` | `GlobalExceptionHandler.handleBadCredentials`/`handleAccessDenied`/лок-аут-хендлер (после LR-026) | credential stuffing, брутфорс — прямой ответ на M10 |
| `auth_login_success_total` | `AuthService.authenticate()` | baseline для аномалий |
| `auth_register_total` | `AuthService.register()` | всплеск регистраций — ранний сигнал перед атакой |
| `authz_denied_total{path,role}` | `handleAccessDenied`/`handleAccessDenied` (тот же хендлер, что уже есть) | попытки обратиться к чужому/админскому ресурсу — прямой ответ на H1 (teacher IDOR) и в целом на класс LR-023 |
| `http_unmapped_path_total{path}` | новый компонент — см. Часть 3 | **ретроспективно самый ценный**: если бы это существовало 2025-10-21..2026-08-06, `GET/PATCH /users`, `/participants` (вне `/api/v1/**`) были бы видны как аномалия с первого дня, не через 9.5 месяцев |
| `backup_job_last_success_timestamp` | Postgres backup CronJob (LR-003) | закрывает уже известный, отдельный пробел — алертинг на бэкап |

**Wysopal:** важное ограничение честности — метрики не заменяют фиксы
LR-024..030, они делают эксплуатацию **видимой**, если она случится, и
сокращают время обнаружения с "9.5 месяцев, пока кто-то не закажет
аудит" до "минуты, пока дашборд не мигнёт". Не путать observability с
security — это соседние, не взаимозаменяемые слои.

### Часть 2 — Сетевая модель: почему это не отдельная задача от NetworkPolicy

**Mackey:** централизованная модель VM600 (project-VM не пушит сама,
VM600 сама скрейпит) — та же логика, что supply-chain-минимализм:
секрет Grafana Cloud токена живёт **в одном месте** (VM600), не
размножается по каждому проекту. Для LR это означает: `/actuator/
prometheus` не должен быть достижим ни для кого, кроме VM600.

**Winch:** это прямо тот же принцип, что обосновал удаление Spring Data
REST в LR-023 — "невозможно по конструкции" сильнее "закрыто
конфигурацией". Правильная реализация — не `@PreAuthorize` на
метрика-эндпоинте (это всё ещё "закрыто конфигурацией", тот же класс
хрупкости), а структурная сетевая изоляция:

1. `management.server.port` — отдельный порт (по образцу numi's `9090`),
   **не тот**, что слушает бизнес-API.
2. Этот порт не публикуется через k3s `Service`/`Ingress` вообще — он
   существует только внутри пода/namespace.
3. `NetworkPolicy` в `lr-dev` (тот самый нереализованный пункт из
   `INFRA-LR.md` §8 и M4 из аудита) — разрешает ingress на этот порт
   **только** с IP VM600 через сегмент `10.10.10.0/24`.

Реализация этого мониторинга — не побочный эффект, а прямая, естественная
**причина** наконец закрыть M4 (NetworkPolicy) и M7 (Actuator на
публичном listener'е) — нельзя правильно подключить VM600, не сделав
и то, и другое одновременно. Роадмап не откладывает эти находки на
"когда-нибудь" отдельным тикетом — он делает их предусловием для
самого мониторинга.

### Часть 3 — "Правильный", не дешёвый CI-guard

**Заказчик спросил конкретно, вписывается ли CI-guard в роадмап — да,
но не тот, что предлагался изначально.**

**Winch:** grep на строку `spring-boot-starter-data-rest` в `build.gradle`
— хрупкая проверка: ловит только этот один, уже известный случай. Другая
зависимость с тем же классом поведения (авто-экспозиция) — например,
если кто-то добавит Spring Boot Admin, или другой auto-configuring
starter, — пройдёт мимо неё незамеченной. Правильная проверка — не имя
зависимости, а **факт**: тестировать реально смонтированную HTTP-
поверхность против allow-листа, тем же способом, что уже доказал себя
в `SpringDataRestExposureTest` (LR-023), но обобщённо, не точечно под
один случай.

**Long:** механизм для этого уже есть в Spring без новых зависимостей —
`RequestMappingHandlerMapping.getHandlerMethods()` возвращает полный
реестр всех замонтированных `@RequestMapping`. Тест, который поднимает
контекст, читает этот реестр и утверждает "каждый путь либо начинается
с `/api/v1/`, либо явно в allow-листе (`/actuator/health`, ...)" — ловит
**весь класс** "что-то незаметно замонтировало HTTP-поверхность вне
нашего API", а не конкретно Spring Data REST. Это и есть источник
метрики `http_unmapped_path_total` из Части 1 — та же логика, реализованная
дважды: один раз как CI-тест (ловит на этапе сборки), один раз как
runtime-метрика (ловит, если что-то всё же проскочило CI, или если кто-то
целенаправленно пробует случайный путь в проде).

**Moussouris:** это и есть институционализация, о которой шла речь в
синтезе Roundtable #4 — не "не забыть про одну находку", а структурный
guard, переживающий любую конкретную находку.

**Mackey:** к этому же слою — SBOM, не разово. `./gradlew dependencies`
как артефакт каждого CI-прогона (или лёгкий CycloneDX Gradle-плагин,
не обязательно сразу полноценный SCA-инструмент) — минимальная версия
"что реально на classpath и зачем" как живой, а не разовый вопрос.

### Синтез (Tech Lead) — фазированный план

быть уже на месте **до** этого расширения ролей, не после первого
инцидента с ним. То же самое верно для реальной оплаты (LR-017,
Stripe/Numi) — платёжный трафик радикально поднимает ставки для всего,
что здесь предложено.

## Roundtable #6 — Frontend UI/UX: состав главной, навигация, дашборды, мобильная версия

**Дата:** 2026-08-08
**Контекст:** прямой запрос заказчика (тикет `LR-048`) — не абстрактное
UX-обсуждение, а анализ best practices каждого эксперта, спроецированный
на реально построенный код `frontend-svelte`, не на текст ADR.
**Формат:** новая панель — эксперты по продуктовому/интеракшн-дизайну,
usability и фронтенд-архитектуре конкретно под этот стек (SvelteKit +
Tailwind), без внутренних голосующих. Синтез — Tech Lead.

**Панель:**
- **Luke Wroblewski** — mobile-first дизайн, конверсия форм ("Mobile
  First", LukeW.com).
- **Jakob Nielsen** (Nielsen Norman Group) — 10 usability heuristics,
  evidence-based UX.
- **Alan Cooper** (Cooper, "About Face") — goal-directed design,
  interaction design, персоны.
- **Rich Harris** — создатель Svelte/SvelteKit, философия "disappearing
  framework", простота через компилятор.
- **Sara Soueidan** — доступность (a11y), архитектура CSS.

### Исходные данные (факты, собраны Explore-агентом по реальному коду
`frontend-svelte`, не по памяти/ADR)

- Навигация — `+layout.svelte`: desktop- и mobile-меню — **два
  раздельных блока разметки**, не общий компонент/список, оба содержат
  идентичный набор пунктов (Home/About/Activities/Workshops/
  Performances + роль-зависимая ссылка + Logout/Login + локаль + тема).
  Мобильное меню уже один раз ловило реальный прод-баг ("завис открытым
  на iPhone 14", исправлено `closeMobileMenu()`).
- Роль-зависимость реализована как **одна** ссылка, у которой меняется
  label/href (Admin→`/admin`, Teacher→`/teacher`, иначе→`/dashboard`) —
  не отдельные меню на роль.
- Admin sub-nav (`admin/+layout.svelte`) — плоский список из 8 пунктов
  (Overview/Users/Activities/Workshops/Groups/Venues/AgeGroups/
  Performances), без группировки.
- Admin overview — один общий loading/error gate на всю страницу поверх
  трёх параллельных fetch'ей; секции: 5 stat-карточек, recent workshops,
  alerts (M5), fill rate (M1), registration trend как **самодельный CSS
  bar chart** (M4, без библиотеки графиков), retention (M6).
- Личный дашборд — тот же паттерн одного общего gate; Payments —
  сырая HTML `<table>`, не компонент.
- Данные везде получаются через `$effect`/`onMount` client-side fetch,
  **не через SvelteKit `load()`** — осознанный выбор из `LR-002`
  (SPA-fallback вместо prerender, потому что страницы client-gated).
- UI-примитивы: `Button`/`Input`/`Select`/`Textarea`/`Card`/`ErrorText`
  — нет `Table`/`Badge`/`Tabs`/`Modal` — таблицы и бейджи собраны inline
  на каждой странице заново.
- Токен-система (`layout.css`): полноценные light/dark семантические
  токены, self-hosted шрифты (DSGVO-осознанно), `prefers-reduced-motion`
  учтён в двух местах. Нет шкалы spacing/radius — ad hoc Tailwind-утилиты.

### Реакции экспертов

**Wroblewski:** Единственный CTA на главной ("Записаться") —
правильно, не размывает решение конкурирующими кнопками. Но мобильное
меню — **не mobile-first по духу**, хоть и адаптивно по факту: это
вторая копия desktop-разметки, а не спроектированный с нуля мобильный
паттерн — отсюда и реальный баг с "зависшим" меню, дублирование состояния
почти всегда порождает именно такие баги. Payments-таблица на узком
экране будет либо горизонтально скроллиться, либо сжиматься до
нечитаемости — карточный вид на мобильном, таблица как progressive
enhancement на широком.

**Nielsen:** "Visibility of system status" нарушена дважды — один
общий gate на 3 параллельных fetch'а значит: упал один запрос — не
видно вообще ничего, вместо частичной деградации по секциям. "Recognition
rather than recall" — одна ссылка, меняющая label в зависимости от
роли, не даёт постоянного визуального индикатора "ты сейчас в
admin-режиме" — только имя ссылки. "Consistency and standards" — раз
таблицы/бейджи собраны заново на каждой странице, а не общим
компонентом, мелкие расхождения (радиус, отступы) неизбежно накопятся,
даже если каждая страница по отдельности выглядит нормально. Отдельный
вопрос не про код: "Activities"/"Workshops"/"Performances" как три
раздельных пункта меню — совпадает ли это с тем, как реальный
взрослый посетитель мысленно делит предложение студии, или это просто
проекция схемы БД (`Activity → Workshop → Group`) наружу? Не решается
дизайном в вакууме — нужна проверка с реальным пользователем/Olena.

**Cooper:** Admin-дашборд смешивает на одном плоском экране
"требует действия сейчас" (alerts, fill-rate warnings) и "как идут дела
у бизнеса" (registration trend, retention) без иерархии — goal-directed
дизайн для админа как персоны требует: то, что требует действия, должно
быть визуально доминирующим и первым, business-health — второстепенным,
менее срочным блоком. Плоский список из 8 пунктов sub-nav уже сегодня
неудобен и будет хуже с ростом — сгруппировать по реальному workflow
(например "Каталог": Activities/Workshops/Performances; "Операции":
Groups/Venues/AgeGroups; "Люди": Users), не по алфавиту/порядку
добавления в код. Expand/collapse участников в Teacher-дашборде —
правильный инстинкт progressive disclosure, не открывать всё сразу.

**Harris:** Дублирование desktop/mobile-разметки в одном файле — не
идиоматично для Svelte: один список пунктов навигации, отрендеренный
`{#each}` в обоих местах (или вообще один блок с CSS-only responsive
через `<details>`), устраняет и дублирование, и целый класс багов вроде
уже случившегося. Отдельный вопрос про `load()` — **исправлено по
находке `architect-reviewer`, см. ниже**: изначальная реакция
недооценила реальную цену вопроса. `hooks.server.ts` в этом проекте
выполняется только на этапе сборки/в `vite dev`/`vite preview` —
`vite.config.ts` использует `adapter-static` с `fallback: 'index.html'`
(чистый SPA-билд, `nginx.conf` отдаёт `try_files ... /index.html`), то
есть на реальном проде **нет** серверного рантайма вообще, который
мог бы исполнить `load()`/`hooks.server.ts` на каждый запрос. Значит
"узкое, осторожное исследование `load()` для дашбордов" на самом деле
означает пересмотр самого решения `LR-002` (SPA-fallback вместо
prerender) целиком — смену адаптера (`adapter-node`/`adapter-cloudflare`
и т.п.), переработку Docker/nginx-образа и k3s-деплоя. Это
принципиально другого масштаба вопрос, чем звучало изначально — либо
явно ставить именно его (стоит ли вообще пересматривать `LR-002`), либо
снять SSR/streaming-обоснование и оставить только достижимую в текущей
SPA-модели часть (секционные loading-состояния — см. Nielsen, это
решается и без `load()`). Отсутствие тяжёлого
UI-кита (`Table`/`Modal`/`Tabs` и т.д.) — правильно, не тащить лишний
вес ради абстракции — но 2-3 паттерна (таблица, бейдж), уже повторяющиеся
inline на нескольких страницах, стоит вынести в реальные компоненты
сейчас, до того как повторение случится в 4-й и 5-й раз и разъедется.

**Soueidan:** Самодельный CSS bar chart (registration trend) — под
вопросом, есть ли текстовый эквивалент для скринридера (голые `div`
с inline `height%` без `aria-label`, скорее всего, ничего не сообщают)
— нужна прямая проверка, не предположение. Severity-бейджи (info/
warning/urgent/critical) — **проверено по находке `architect-reviewer`:
уже в порядке**, `admin/+page.svelte`'s `levelLabel[a.level]` рендерит
текстовую подпись уровня рядом с цветом, не только цвет — WCAG 1.4.1
не нарушается, вычёркивается из списка находок, не тикетится. Кнопка
гамбургер-меню — конкретно этот элемент уже один раз давал реальный
прод-баг, стоит целевого аудита именно на `aria-label`/`aria-expanded`,
не общего прохода по всему сайту. `prefers-reduced-motion`, учтённый
в двух местах, и осознанное разделение semantic error/success от
brand-акцентов в токенах — сделано правильно, стоит явно похвалить, не
только критиковать. Отсутствие шкалы spacing/radius (только ad hoc
Tailwind-значения) — тот же класс риска расхождения, что и
"Consistency" у Nielsen, только со стороны CSS-архитектуры, а не
психологии восприятия.

### Синтез (Tech Lead)

Приоритизировано по тому же принципу, что и общая ретроспектива бэклога
— не механически "один пункт эксперта = один тикет", а по реальному
пересечению находок нескольких экспертов сразу:

1. **Единая навигация** (Harris + Nielsen + Wroblewski, все трое
   независимо пришли к одному выводу) — общий источник пунктов меню,
   не дублированная разметка. Устраняет целый класс багов, не только
   косметика.
2. **Секционные loading/error состояния** на admin- и личном дашборде
   (Nielsen) — вместо одного общего gate на всю страницу.
3. **Пересмотреть `LR-002` (SPA-fallback) целиком, не "узкое
   исследование `load()`"** (Harris, исправлено по `architect-reviewer`) —
   `hooks.server.ts`/`load()` не исполняются на реальном проде под
   текущим `adapter-static`, значит вопрос — "стоит ли менять адаптер
   и переделывать Docker/nginx/k3s-деплой ради SSR", не мелкая доработка.
   Отдельный, дорогой по объёму скоуп, явно поставить вопрос именно так.
4. **Реорганизация admin-дашборда**: группировка sub-nav по workflow +
   иерархия "требует внимания" выше "здоровье бизнеса" (Cooper) — одна
   и та же страница, один диф.
5. **Мобильный вид Payments-таблицы** — карточки на узких экранах
   (Wroblewski).
6. **Точечный a11y-аудит**: текстовый эквивалент bar chart, проверка
   severity-бейджей на не-только-цвет, `aria-label`/`aria-expanded` на
   гамбургере (Soueidan) — приоритет гамбургеру, он уже показал себя
   источником багов.
7. **Вынести `Table`/`Badge` в реальные компоненты** (Harris + Nielsen
   consistency) — не срочно, но чётко обозначенный порог "повторилось
   3+ раз — пора".
8. **Проверить номенклатуру Activities/Workshops/Performances** с
   заказчиком/Olena (Nielsen) — продуктовый вопрос, не инженерный,
   не решать в одиночку.

**Отмечено отдельно, не как срочная находка:** дизайн-система токенов,

### Реакции экспертов

**Volz:** Уточнение к уже принятой на Roundtable #5 модели (один
коллектор, per-project `scrape_configs`), не новое решение с нуля.
Схема именования метрик между проектами не должна означать
"добавить префикс `lr_`/`numi_` к каждому имени" — это ломает главную
ценность единой ноды: возможность написать **один** PromQL-запрос
(`sum by (job) (rate(auth_login_failure_total[5m]))`) и увидеть все три
проекта на одном графике задаром. Разграничение уже даётся бесплатно
через `job`/`instance`-лейблы `scrape_configs` (`job_name:
'numi-backend'` и т.п.) — держать одинаковую СЕМАНТИКУ метрики под
одним именем там, где концепция общая (login-failures, unmapped-paths,
authz-denials), разное — где она реально разная. Отдельно: `LR-031`'s
решение НЕ тегировать `authz_denied_total`/`http_unmapped_path_total`
raw-путём — абсолютно верное решение по cardinality-гигиене, и это
правило должно стать явным для всех трёх проектов на единой ноде, не
молчаливым соглашением одного LR — соблазн добавить `path`/`user_id`
"just for debugging" сильнее именно на общей платформе, где кажется,
что расходы размазаны.

**Long:** LR's паттерн (Micrometer → `/actuator/prometheus`, отдельный
management-порт, `NetworkPolicy`-скоуп на IP коллектора) должен стать
задокументированным стандартом для любого будущего Spring-сервиса на
этой инфре, не переоткрываться с нуля каждый раз — то, что уже сделано
для LR, буквально уже проверенный рецепт. numi (Go) и workout-evo
(стек неизвестен) не смогут переиспользовать Micrometer напрямую, но
должны фидить те же лейбл-конвенции (Volz) на выходе — контракт про
"как выглядит метрика на выходе" общий, "как её получить" —
идиоматично для каждого стека отдельно.

**Majors:** "Единая нода" решает проблему СБОРА, не проблему
observability — вопрос не "где стоит коллектор", а "могу ли я задать
произвольный вопрос, который не предусмотрел заранее, быстро, по всем
трём проектам". С counter'ами и дашбордами (текущий подход и LR, и
numi) это по определению не так — видно только то, под что заранее
построена панель. Для масштаба этого проекта (домашний сервер, один
администратор) — это осознанно достаточный компромисс, не повод
переезжать на high-cardinality трейсинг — но роундтейбл должен явно
зафиксировать: это "мониторинг", не полная "observability", и это
осознанный, а не случайный выбор уровня инвестиции. Отдельно: весь
список кандидатов на alert (из `LR-031` роадмапа) — security-специфичен;
нет ли отдельного, более базового "жив ли сайт вообще, не деградировала
ли задержка" мониторинга, общего для всех трёх проектов, а не только
security-сигналов? (UptimeRobot упоминается в доках numi как более
грубая проверка — стоит явно подтвердить, не предполагать, что этого
достаточно.)

**Fong-Jones:** Самая конкретная и самая срочная точка всего
роундтейбла — канал уведомлений не решён ни для одного из трёх
проектов, и это и есть реальный блокер, не схема метрик. Алерт, которому
некуда прийти — хуже отсутствия алерта: даёт ложную уверенность "у нас
есть мониторинг" без работающей половины — доставки. Для
single-operator домашнего сервера (не 24/7 on-call команда) — лёгкий
канал: Telegram-бот через встроенный Grafana Cloud contact point (просто,
бесплатно, push на телефон) — разумный дефолт, если у заказчика нет
готового предпочтения; Slack избыточен для одного человека. **Уточнение
по находке `architect-reviewer`:** это отдельный бот/токен от уже
упомянутого в `LR-ADR-016` кандидата на Telegram как канал
клиент-facing напоминаний в личном кабинете (другая цель, другая
аудитория) — не переиспользовать один и тот же токен/бот для обеих
задач. Риск утечки токена ниже, чем у самостоятельно хостящегося бота
— он живёт в конфиге Grafana Cloud's contact point, не в секретах
k3s-проекта — но именно поэтому важно не смешать его с
клиент-facing ботом, который такой изоляции не имеет по умолчанию. Не
формализовывать SLO/error budget — рано для этого масштаба зрелости —
но выбрать 2-3 alert'а "если сработал — смотреть сегодня" на проект как
v1, не строить полный каталог алертов раньше, чем доставка проверена
живьём хотя бы один раз.

**Gregg:** VM600 должна мониторить сама себя (USE-метод — Utilization/
Saturation/Errors), не быть только коллектором ДЛЯ других: CPU/память/
диск самой ноды, не захлёбывается ли процесс коллектора, не падают ли
скрейпы. Если VM600 тихо ляжет, все три проекта разом теряют
мониторинг одновременно — и, возможно, никто не заметит именно
потому, что мониторинг сам и есть то, что должно было заметить. Плюс:
не размещать VM600 на уже перегруженной роли (`gateway-core`,
LR-BUG-05) — тот же урок, что уже стоил инцидентов в этом проекте.
**Тот же принцип уже нарушен на VM300** (найдено по находке
`architect-reviewer`, не было в исходном инвентаре): это одновременно
прод-хост numi (`numi.service` + текущий project-specific
`otelcol-contrib`) и k3s-worker для workout-evo — сегодня безопасно
только потому, что workout-evo намеренно остановлен; при реальном
запуске workout-evo это станет тем же классом риска, что и
`gateway-core`, стоит явно решить до, не после. Скрейпить нужно не
только app-level метрики (`/actuator/prometheus`-
стиль), но и host-level (`node_exporter` на всех VM, не только
project-нодах) — иначе видно "приложение X тормозит", но не "потому что
у ноды кончилась память" — именно такого рода проблема уже реально
случалась в этом гомлабе (NAT-правило, перегрузка gateway-core).

### Синтез (Tech Lead)

1. **Схема именования метрик** — общая семантика/имя там, где концепция
   общая, разграничение через `job`-лейбл, не префиксы (Volz) —
   задокументировать как явный контракт, не молчаливое соглашение.
2. **Канал уведомлений — решить сейчас, не откладывать в третий раз**
   (Fong-Jones) — дефолт-кандидат Telegram-бот через Grafana Cloud
   contact point, если у заказчика нет другого предпочтения.
3. **VM600 должна мониторить саму себя** — USE-метрики хоста +
   здоровье коллектора (Gregg) — не только быть каналом для остальных.
4. **Размещение VM600** — явно не на уже перегруженной роли
   (`gateway-core`) (Gregg + `LR-BUG-05`).
5. **Явное признание уровня зрелости**: это мониторинг, не полная
   observability — осознанный выбор под масштаб проекта (Majors), не
   повод недоинвестировать позже, когда/если масштаб изменится.
6. **v1 alert-лист** — уже существующий список `LR-031`-роадмапа
   (security-сигналы) + базовая доступность/латентность (Majors) — не
   разрастаться в полный каталог до проверки доставки хотя бы одного
   алерта живьём (Fong-Jones).
7. **Spring/Micrometer-паттерн LR — задокументировать как переиспользуемый
   стандарт** для будущих Spring-сервисов; numi/workout-evo фидят те же
   лейбл-конвенции своим идиоматичным способом (Long).

**Не начинать `LR-031` Фазу 3 без пп. 1-2 выше** — иначе риск построить

numi/workout-evo подключатся к тому же VM600 следующими.

## Roundtable #8 — Модель расписания/периодичности `Course`

**Дата:** 2026-08-09
**Контекст:** `LR-ADR-021` выделил `Course` в отдельную сущность, но
явно отложил вопрос "как хранить регулярность занятий" сюда —
несколько технически валидных подходов, ставки высоки (эпик юридически
срочен, переделка после факта дорога). Тикет `LR-068`, гейтит `LR-069`
(Course-backend) и `LR-075` (форма создания Course).
**Формат:** новая панель, подобранная под конкретный инженерный вопрос
(не безопасность/UX/мониторинг, как в прошлых роундтейблах) — эксперты
по паттернам повторяющихся событий, границам доменных агрегатов и
content-as-data архитектуре. Без внутренних голосующих, синтез — Tech
Lead.

**Панель:**
- **Martin Fowler** — автор канонического паттерна "Recurring Events for
  Calendars" (разделение "правила повторения" и материализованных
  "occurrences", с явной поддержкой исключений на уровне отдельного
  occurrence).
- **Vaughn Vernon** — Domain-Driven Design, границы агрегатов (когда
  структура должна материализоваться в отдельные записи, а когда
  оставаться вычисляемым свойством).
- **Karen McGrane** — content-as-data / структурированный контент
  ("Create Once, Publish Everywhere") — релевантна напрямую для
  ZFU-требования "один источник текста для сайта и для письма в
  ведомство", не только для расписания как такового.
- **Josh Long** — Spring/JPA-специфика (преемственность с уже принятыми
  в проекте решениями, Roundtable #4/#5/#7) — как это ляжет на реальный
  стек, не абстрактно.

### Исходные данные (факты, не мнение)

- `Group` уже сегодня — доказанный паттерн "конкретное проведение":
  `Workshop` (описательная сущность, без расписания с `LR-015`) → много
  `Group` (своя вместимость/список участников/учитель/venue/расписание
  на каждую). Заказчик описал для `Course` **тот же паттерн**: "1 Курс
  может быть проведён для разных Групп... и с разными учителями... в
  разных локациях."
- `LR-067` (закрыт) уже дал `Group` дочернюю сущность `Session` —
  материализованные дни под одним `Group` с общим списком участников.
  Сейчас используется для 1-10-дневных Workshop-марафонов, но
  архитектурно ничем не привязана именно к короткому диапазону дней.
- `Enrollment.java` (реальный код): `workshop` — `@ManyToOne(optional =
  false)`, то есть **обязательное** поле сегодня. Если `Course`
  регистрирует участников через `Group` без связанного `Workshop`, это
  ограничение ломается — требует правки схемы, не решено предыдущими
  ADR (`LR-ADR-021` добавил `courseId` только на `Workshop` и
  `Performance`, не на `Enrollment`/`Group`).
- ZFU-бриф (`docs/compliance/tlab29-zfu-compliance-brief.md` §2)
  требует единого источника текста-дисклеймера ("держать формулировки
  в одном источнике... чтобы сайт и письмо в ZFU не разъехались") —
  структурная, не только текстовая задача.
- Масштаб: курс длится 1 месяц – 1 год, 1-3 занятия/неделю → максимум
  порядка 150 занятий на курс за весь период. Не big-data задача —
  материализация всех occurrences сразу, без ленивой генерации,
  вычислительно тривиальна.

### Реакции экспертов

**Fowler:** Мой собственный паттерн разделяет "правило повторения"
(когда/как часто) от "occurrences" (конкретные материализованные
даты) — и критично: **каждый occurrence должен быть независимо
редактируемым/отменяемым** без разрушения общего правила (пропуск
занятия на праздник, перенос одного занятия и т.д. — обычная жизнь
курса длиной в месяцы). Это ровно то, что уже даёт `Session` из
`LR-067`: если `Course`'s `Group` получит поле "правило повторения"
(дни недели + время + диапазон дат) и при сохранении генерирует
реальные `Session`-строки на каждую подходящую дату — это тот самый
паттерн, без необходимости RRULE-библиотеки (её мощь — таймзоны,
редкие/сложные правила повторения, месячные/годовые интервалы — не
нужна для "по Пн и Ср, раз в неделю", это оверинжиниринг под этот
масштаб). Материализовать сразу, не лениво — при 150 занятиях максимум
это не вопрос производительности.

**Vernon:** Вопрос agregate-границ здесь уже фактически решён прошлыми
тикетами, просто не проговорён явно для `Course`: `Group` — это то
место, где реально живёт "конкретное проведение" (учитель, зал,
вместимость, список участников) — и именно `Group`, не `Course`,
должен нести поле правила повторения, ровно по тому же принципу, что
`Workshop` избавился от расписания в пользу `Group` (`LR-015`). `Course`
остаётся чисто описательной/маркетинговой сущностью (название,
описание, формат, комплаенс-поля) — **без единого поля расписания** —
ровно то же разделение ответственности, что уже доказало себя для
`Workshop`. Разные `Group` одного `Course` могут иметь разные правила
повторения (группа по Пн/Ср и группа по Вт/Чт того же курса) — это
корректно поддерживается, если правило живёт на `Group`, а не на
`Course`.

**Long:** Технически это означает: `Group` получает `courseId`
(nullable, рядом с уже существующим `workshopId` — ровно та же
mutual-exclusivity полулогика, что уже была принята для `Workshop.
courseId`/`Performance.courseId` в `LR-ADR-021`) плюс новые поля
`recurrenceDaysOfWeek`/`sessionStartTime`/`sessionEndTime` (используются
только когда `courseId` задан). Генерация `Session`-строк из правила —
метод в уже существующем `SessionService` (`LR-067`), не новый сервис —
переиспользование, не дублирование. **Реальный пробел, который иначе
остался бы незамеченным до продакшена:** `Enrollment.workshop` сейчас
`@ManyToOne(optional = false)` — обязательное поле. Регистрация на
`Course`-группу без `Workshop` не пройдёт валидацию как есть. Нужен
отдельный тикет: `workshop` → nullable, плюс новое nullable `course`
поле на `Enrollment`, тот же паттерн, что уже применён к `Workshop`/
`Performance`.

**Расширено по находке `architect-reviewer`:** пробел на `Enrollment`
глубже, чем два nullable-поля. `EnrollmentService.enroll(workshopId,
...)` принимает `workshopId` как основной параметр и выводит
`PENDING`/`CONFIRMED` из `workshop.getPrice()` — у `Course` (по этой же
синтезированной модели) вообще нет поля цены, значит нужен либо
параллельный метод `enrollInCourse`, либо цена переносится на `Course`
отдельным решением. `EnrollmentController` сегодня публикует только
`POST /workshops/{workshopId}/enroll` — нужен новый route, не только
схема. `Order.java` — тот же паттерн, FK только на `Workshop`; если
платные Course когда-либо появятся (правдоподобно при длительности
"1 месяц – 1 год"), там та же дыра. И `uk_user_workshop` (unique на
`user_id, workshop_id`) не даёт защиты от дублей после того, как
`workshop_id` станет nullable — Postgres считает `NULL` уникальным
относительно себя в unique-constraint, значит нужен либо
`uk_user_course`-аналог, либо app-level guard в новом
`enrollInCourse`. Follow-up тикет должен покрывать все четыре пункта,
не только nullable-поля на `Enrollment` — иначе Course-регистрация
упрётся в стену при первой реальной попытке её реализовать.

**McGrane:** Отдельно от структуры расписания — ZFU-требование "один
источник текста" нужно решить на уровне `Course`, не `Group`/`Session`
(комплаенс-текст — свойство курса как продукта, не конкретного
проведения). `Course` должен получить: `isOnline`/`isSynchronous`/
`hasRecordings` (булевы, по которым можно программно валидировать
консистентность — если `hasRecordings=false`, UI не должен даже
позволить вставить слово "Aufzeichnung" рядом с описанием) плюс единое
поле `formatDisclaimer` (мультиязычное, как `titleDe/En/Ua`) — сайт
рендерит именно это поле, не отдельно написанный на каждой странице
текст. Не решать вопрос "как хранить" раздельно от "что хранить" — они
связаны: если бы `Course` хранил только свободный текст описания без
структурных флагов, риск разъехаться с письмом в ZFU остался бы прежним,
просто в новом месте.

**Уточнено по находке `architect-reviewer`:** бриф (§2) требует ещё
двух утверждений — "только для взрослых" и "без экзаменов/сертификата/
диплома/квалификации" — которые предложенные три булевых флага не
покрывают. Осознанное решение, не пропуск: у этих двух утверждений нет
противоречивого UI-состояния, которое нужно было бы структурно
блокировать (в отличие от "запись есть, но текст говорит, что записи
нет") — они остаются свободным текстом внутри `formatDisclaimer`,
проверяемым тем же ручным compliance-процессом (человеческое
согласование перед публикацией, см. бриф), не отдельными булевыми
полями. Асимметрия с остальными тремя флагами — намеренная, не
недосмотр.

### Синтез (Tech Lead)

**Итоговая модель:**
1. `Course` — чисто описательная сущность: `titleDe/En/Ua`,
   `descriptionDe/En/Ua`, `ageGroupId`, `isOnline`/`isSynchronous`/
   `hasRecordings` (булевы флаги, McGrane), `formatDisclaimerDe/En/Ua`
   (единый источник ZFU-текста). **Без полей расписания вообще** —
   тот же принцип, что уже применён к `Workshop` (Vernon).
2. `Group` — расширяется: `courseId` (nullable, рядом с существующим
   `workshopId`), `recurrenceDaysOfWeek`/`sessionStartTime`/
   `sessionEndTime` (используются только при заданном `courseId`).
   Одна `Group` = одна вместимость/список участников на весь курс,
   независимо от количества занятий (тот же принцип, что уже доказан
   `LR-ADR-022` для многодневных Workshop). Диапазон дат курса —
   существующие `Group.startDateTime`/`endDateTime` (первая/последняя
   дата генерации `Session`), без новых полей: то же переиспользование,
   что уже действует для многодневного Workshop (`startDateTime` = день
   1), только `endDateTime` здесь обязателен для Course-группы (у
   Workshop он опционален) — **уточнено по находке `architect-reviewer`**,
   чтобы не остаться неявным смысловым overload.
3. `Session` (`LR-067`, уже реализована) — переиспользуется без
   изменений структуры: при сохранении `Group` с заданным правилом
   повторения `SessionService` генерирует реальную `Session`-строку на
   каждую подходящую дату в диапазоне (Fowler — материализация, не
   ленивое вычисление, масштаб позволяет). **Уточнено по находке
   `architect-reviewer`:** существующий `replaceSessionsForGroup`
   (`LR-067`) — деструктивный clear+re-add (проверено
   `SessionIntegrationTest` на реальном Postgres), при повторной
   генерации сотрёт любые ручные правки отдельных `Session` (перенос
   одного занятия и т.п.) — то самое исключение, ради которого Fowler
   вообще выделяет occurrence-уровень. При масштабе Workshop (≤10 дней,
   весь список пересылается разом при каждом сохранении) это не
   создавало риска; при масштабе Course (до ~150 занятий, месяцы жизни)
   — создаёт. Принятый компромисс: регенерация запускается **только**
   когда реально меняются поля правила повторения
   (`recurrenceDaysOfWeek`/`sessionStartTime`/`sessionEndTime`/диапазон
   дат), не при любом сохранении `Group` —guard на уровне
   `GroupService`, не на каждый save. Ручные правки отдельных `Session`
   после генерации сохраняются до следующей регенерации правила;
   повторная регенерация их сотрёт — это осознанно принятый trade-off
   (не полное соответствие Fowler-паттерну), административный UI
   (`LR-074`/`LR-075`) обязан явно предупреждать об этом перед
   регенерацией.
4. **Найденный по пути реальный пробел, не предрешённый прошлыми ADR:**
   `Enrollment.workshop` сегодня обязателен — нужен отдельный тикет
   (nullable `workshop` + новое nullable `course`), иначе регистрация на
   курс технически невозможна на уровне схемы. **Расширено по находке
   `architect-reviewer`** (см. реакцию Long выше) — тикет должен также
   покрыть `EnrollmentService.enroll`/новый `enrollInCourse`-путь,
   `EnrollmentController`'s новый route, `Order`'s тот же
   workshop-only-FK паттерн и замену `uk_user_workshop` на
   app-level/parallel-constraint защиту от дублей для Course.
5. **Добавлено по находке `architect-reviewer`:** mutual-exclusivity
   между `Group.workshopId` и `Group.courseId` (как и между
   `Workshop.courseId`/`Performance.courseId` из `LR-ADR-021`) сегодня
   нигде не enforced — ни CHECK-constraint в БД, ни валидация в
   `GroupService`, это пока непроговорённая конвенция, не реальный
   механизм. `GroupService.createGroup` должен получить явную проверку
   "ровно один из workshopId/courseId задан" как часть `LR-069`/
   downstream-тикета на расширение `Group`, а не остаться допущением.

**Не выбрано и почему:** RRULE-подобное хранение (Fowler — мощь не
нужна под этот масштаб, лишняя библиотека и сложность парсинга ради
"по Пн и Ср"); отдельная от `Group`/`Session` параллельная структура
специально для `Course` (Vernon — дублирование уже доказанного
паттерна без причины); хранение комплаенс-текста как обычного
свободного описания без структурных флагов (McGrane — не решает
реальный риск разъехаться с письмом в ZFU, просто переносит его).
