# Roundtable Log — Lebens Rhythmus

"Рыцари круглого стола" — формат по образцу `numi/docs/decision-history/roundtable-log.md`.

**Правила:** Enthusiast-Adventurer — 2 голоса (двигатель прогресса, максималист).
Внешние эксперты спорят pro/con из своей области, канализируя их
публично известную инженерную/дизайнерскую/бизнес-философию — **не
выдуманные цитаты, не буквальные высказывания реальных людей**, та же
конвенция, что и в numi Roundtable #4. Tech Lead синтезирует и
финализирует. Лог хранится не как решение, а как ответ на вопрос "почему
мы решили X" — через месяцы, когда контекст забудется.

**Дистиллированные решения (ADR) — не здесь, а в
[`docs/architecture/decisions.md`](../architecture/decisions.md).** Этот
файл — полный нарратив, тот в свою очередь — сухой остаток.

### Phase 0 — Брифинг: LR на 20.07.2026

Java 21 / Spring Boot 3.5.7 / Gradle, PostgreSQL 16, Spring Security + JWT
(HS256), статический MPA-фронтенд без фреймворка (18 страниц), k3s на
домашнем сервере, GitLab CI, Cloudflare Tunnel (`cf_worker_lr.js` —
неиспользуемый артефакт, подтверждено владельцем: реальный путь трафика
через CF Tunnel, не через Worker).

Архитектура — слоистая (controller→service→repository→entity), задумана
гексагональной, по факту нет: JPA прошита прямо в domain-классы, портов
для внешних систем нет, потому что внешних систем нет вообще. БД без
миграций (`ddl-auto=update` + runtime ALTER-костыль), без бэкапов, без
HA. Безопасность: JWT_SECRET plaintext в Helm при том, что DB-пароль
защищён правильно; один контроллер без `@PreAuthorize`; хеширование
пароля дважды почти ломалось за 7 месяцев. Фронтенд: мультиязычность
(DE/EN/UA) уже в БД (`Activity`, `Group`), нигде не используется.

Бизнес-контекст: разрыв "нет платежей" породил отдельный проект (Numi) —
интеграция LR↔Numi решена только на уровне идеи.

Продуктовый wishlist от Olena (неприоритизированный): презентационный
сайт с топ-UI/UX и видео; регистрация + личный кабинет с дневником и
напоминалками; дашборд админа-режиссёра; оплата (Numi + Stripe +
другие); AI-промо в соцсетях/WhatsApp/Telegram; "всё для ERM, что не
описано"; рекомендации по must-have для PWA.

### Phase 1 — Вопросы панели (полный текст сохранён построчно — 17
голосов, ~30 вопросов). Ключевые темы:

- **Мартин/Эванс** — есть ли формальные инварианты (нет, только
  устаревшая ERM-диаграмма); сколько бизнес-правил переживут смену
  схемы/ORM; кто владелец правды о расписании.
- **Gosling/Johnson/Goetz** — состав команды (соло + AI); принципиальность
  build-инструментов (не принципиально); состояние auth-кода (подозрение
  на AI-IDE автосгенерированный хардкод); готовность инвестировать в
  качество vs скорость.
- **Harris/Osmani/Norman** — кто поддерживает фронтенд после старта; кому
  верить в выборе Svelte; целевые устройства по производительности;
  портрет пользователя личного кабинета; референсы стиля.
- **Hightower/Vogels/Russinovich** — реалистичный рост нагрузки за год;
  psychological status `lr-dev` (dev или уже прод); ценность текущих
  данных; твёрдость даты инфра-апгрейда; кто имеет доступ к кластеру.
- **Hunt/Schneier** — сколько реальных пользовательских данных сейчас;
  модель угроз (кто реальный противник).
- **Momjian/Kerstiens** — объём данных, готовность пересоздавать схему с

- **Cagan/Godin** — чью проблему решает "дневник занятий"; какая ОДНА
  вещь важнее всего через полгода; что реально приводит новых участников.

### Phase 2 — Рекомендации must-have / по максимуму (п.4.7)

**Enthusiast (2 голоса):** минимум — настоящий PWA (offline, "Add to Home
Screen"), Stripe для быстрых разовых оплат, мультиязычность DE/EN/UA
(фундамент уже есть), видео/фото-портфолио с согласия родителей. По
максимуму — AI-черновики постов в соцсети по факту занятия, WhatsApp-бот
"есть ли места", интеграция с Google/Apple Calendar.

**Контрголос (Kerstiens/Momjian/Vogels):** сначала данные не теряются →
авторизация не течёт → миграции версионируются → потом уже AI-эффекты.
Порядок, не отмена списка.

### Phase 3 — Предварительное видение v1 (черновик-гипотеза)

PWA с офлайном, DE/EN/UA, личный кабинет (форма зависит от ответа
Cagan), дашборд Olena, двойная оплата (Numi + Stripe), AI как инструмент
промо (не автономный бот), реальные миграции, реальные бэкапы,
JWT_SECRET через Secret, частичное отделение домена от JPA. Не решено:
фреймворк, масштаб команды, модель угроз, приоритет "одна главная вещь",
судьба Cloudflare Worker-файла, твёрдость даты инфра-апгрейда.

### Round 2 — ответы владельца + живое исследование UI

**Ответы на Phase 1 (дословный смысл сохранён):**

- **Мартину:** формальных инвариантов нет, только несовершенная
  ERM-диаграмма. Не все 17 сущностей нужно разделять — но нужна

  всего проекта и без слома по цепочке половины кодовой базы.
- **Эвансу:** да, была мысль о преподавателях-субподрядчиках со своими
  курсами — усечённые права администратора == роль "Преподаватель" с
  возможностью создавать расписание и состав групп (по времени, по
  возрасту, по вместимости) и резервировать помещения в общем графике
  лаборатории. Формальной проверки/реализации пока нет, только задумка.
- **Гослингу:** команда — я один + Claude Code. Build-tool не
  принципиален (личная неприязнь к Maven POM.xml — вероятно, просто
  недостаточный опыт с ним, не объективная оценка).
- **Джонсону:** auth — "почти хардкод от AI-IDE", нужна глубокая ревизия
  и вероятна полная перестройка хеширования, с шифрованием чувствительных
  полей (персональные/банковские данные) по GoBD/DSGVO. Качество,
  надёжность, гибкость — высший приоритет, время инвестировать готов.
  Согласен на осознанное дублирование модулей, если это повышает
  гибкость/читаемость/модульность.
- **Гётцу:** "спешка, хорошая лишь при ловле блох" — нужно и
  проинспектировать модель, и поддержать миграцией.
- **Харрису:** старт — я + Claude, возможно фронтендер позже. Текущего
  фронтенда почти нет содержательно — весь под снос, держаться не за что.
- **Османи:** offline/PWA — очень хотелось бы, но не первый приоритет
  (тикет создаём). Целевая аудитория по устройствам — средний немец (уже
  "ниже среднего" по благосостоянию) + готовность "быстро ползать" на
  слабых индийских Android.
- **Норману:** пользователи — от подростков (регистрируют по закону
  родители) до буквально бабушек, оба конца спектра должны быть
  впечатлены. Референсов на конкретные сайты сознательно нет — ставка на
  непохожесть, полный собственный ресёрч фич, не копирование трендов.
- **Хайтауэру:** рост в этом году небольшой, со следующего года
  ожидается, целевой ориентир — 100 постоянных участников за год.
  `lr-dev` психологически уже прод.
- **Вогельсу:** текущие данные не имеют ценности — можно сносить и
  строить заново правильно. Дата инфра-апгрейда нетвёрдая, окно
  сентябрь-ноябрь.
- **Руссиновичу:** доступ к кластеру — только я.
- **Ханту:** реальных данных нет, только 3 тестовых аккаунта — все члены
  семьи.
- **Шнайеру:** реалистичный противник — первый и последний из
  предложенного списка: случайный бот-сканер портов **и** state-level
  actor. Не конкурент, не обиженный участник.
- **Момджиану:** данных мало — пересоздаём правильно, с миграциями.

**Живое исследование факта (не мнение):** живой браузер и WebFetch не
смогли достучаться до `tlab29.com` (403/таймаут — вероятно, Cloudflare),
поэтому UI изучен напрямую по реальному исходнику трёх страниц из этого
репозитория (`frontend/pages/{home/index,login/login,about/about}.html`,
`frontend/styles/main.css`):

- Главная страница — один экран: заголовок, подзаголовок, абзац, две
  кнопки. Ни программ, ни галереи, ни отзывов, ни видео.
- About — один блок, фоновая картинка `pyramid.jpg` (тематически не
  связана с театром), один абзац текста. Ни истории, ни лиц, ни команды.
- Ноль дизайн-системы: `main.css` не содержит ни одной CSS-переменной,
  единственное объявление шрифта — `font-family: sans-serif`.
- Баг: `lang="en"` на главной и About при полностью немецком тексте
  (только `login.html` помечен верно, `lang="de"`).
- "Passwort vergessen?" ведёт на `href="#"` — мёртвая ссылка, функции
  восстановления пароля нет ни на фронте, ни на бэке.
- Минимальная длина пароля в форме регистрации — 6 символов.
- Плюс найденный: форма регистрации корректно разносит два отдельных
  GDPR-чекбокса (AGB / Datenschutz) с реальными ссылками — единственный
  участок текущего UI, сделанный добросовестно.

**Ответы на оставшиеся вопросы (Cagan/Godin), плюс новый факт о залах:**

- **Кагану:** "дневник занятий" решает проблему и админа, и

- **Годину:** привлекает участников не "что", а "кто" — сама Olena.

  арендованы, локация нестабильна — может меняться под конкретный

### Round 2 — реакции панели

- **Мартин:** конкретный кандидат на эталон domain/persistence-разделения
  — `Group`/`Workshop`, потому что именно туда бьёт роль "Преподаватель".
  Не браться за все 17 сразу.
- **Эванс:** субподрядчики-преподаватели — полноценный bounded context
  "Faculty Management", не косметика поверх роли `TEACHER`. Хорошая
  новость: в коде уже есть частичный скелет (роль `TEACHER` существует, с
  несколькими read-эндпоинтами по `teacherId`) — не с нуля. Про залы: в
  модели уже разделены `Event.venue_id` и `Workshop.venue_id` — точечная
  привязка зала к конкретному событию архитектурно уже заложена, не
  хватает UI, который это использует.
- **Джонсон:** "почти хардкод от AI-IDE" подтверждает асимметрию
  JWT_SECRET/DB-пароль, найденную в `ARCHITECTURE_OLD.md`. Field-level
  шифрование — через `AttributeConverter`/`@Convert` на уровне JPA-колонки
  или отдельный порт `EncryptionService` (граница — вопрос к Мартину).
  Владелец кластера один — снимает срочность "чужого доступа", не снимает
  вопрос качества.
- **Харрис:** "всё в утиль" упрощает работу — не нужно проектировать
  частичную миграцию 18 страниц, можно строить с нуля сразу под
  архитектуру компонентов.
- **Хайтауэр/Вогельс/Момджиан (синтез):** ~100 участников/год = почти
  нулевая инфра-нагрузка, данные не ценны — значит схему БД и миграции
  можно и нужно пересоздавать СЕЙЧАС, не дожидаясь осеннего апгрейда
  железа. Это две разные шкалы времени, которые ранее смешивались:
  схема/миграции — не привязаны к железу; HA/бэкапы/апгрейд — привязаны
  к окну сентябрь-ноябрь.
- **Хант/Шнайер (синтез):** 3 тестовых аккаунта = лучшее возможное окно
  для перестройки auth/шифрования, пока цена ошибки минимальна. Модель
  угроз (боты + state actor, не инсайдер/конкурент) — приоритет защите от
  automated scanning и криптогигиене выше, чем защите от инсайдерской
  угрозы.
- **Каган:** MVP-периметр от владельца буквально совпал с тремя
  страницами, только что изученными в реальном коде (Home + About +
  Login/Register) — хорошая конвергенция.
- **Годин:** корректирует предложение Enthusiast'а из Phase 2 — AI не
  заменяет Olena в соцсетях, а даёт ей лёгкие инструменты быстро
  делиться моментом.

  спектакли — "пока не думали", не блокирует ничего.
- Логотип есть, цвета — свободны.
- Контент после запуска — Olena сама, редко (пару раз в месяц) — не
  нужен сложный CMS.

### Часть 1 — Что произошло и почему это прозевали

**Moussouris:** Это не "забыли поставить аннотацию" — это решение о
зависимости, принятое без соответствующего threat model, на этапе
scaffolding, и никогда не пересмотренное. Характерно, что это
обнаружилось не при обычном код-ревью, а при первом целенаправленном
аудите именно поверхности атаки — потому что обычное ревью проверяет
код, который написали, а не то, что фреймворк молча включает сам.
Именно для таких вещей и существует практика bug bounty: внешняя
сторона, реально пробующая входные данные против живой поверхности, а
не читающая diff.

**Mackey:** Строка в `build.gradle` появилась практически день в день с
основанием бэкенда — классический артефакт из Spring Initializr или
скопированного стартера, не осознанное решение. Ни разу не
пересмотренная зависимость — это ровно то, для чего существует
SBOM/PBOM-практика: "что реально работает и почему" должен быть живым,
непрерывно проверяемым вопросом, не разовым выбором при scaffolding.
Полное дерево зависимостей (`./gradlew dependencies`) для этого проекта
запрашивалось за 9.5 месяцев ровно один раз — сейчас, в рамках LR-022.

**Wysopal:** Форма ошибки та же, что у уже закрытого в этой же сессии
LR-020 (Bean Validation без провайдера) — код, который синтаксически
корректен, выглядит как обычный Spring Boot проект, и никогда не был
проверен под реальным runtime-поведением. Неважно, попал ли чекбокс в
Spring Initializr от человека или от AI-ассистента — режим отказа
одинаковый. Две находки одной формы в одном проекте за одну сессию — это
не совпадение, это структурный пробел в процессе верификации, не два
independent glitches.

**Winch:** `SecurityConfig`'s `.anyRequest().authenticated()` отработал
ровно так, как спроектирован — как safety net, а не как замена
пообъектным решениям об авторизации. Реальный пробел: авто-
сгенерированные Spring Data REST контроллеры (`RepositoryEntityController`
и т.д.) никогда не проходили через реальную модель авторизации этого
приложения (`@PreAuthorize` на каждом хендрайтен-контроллере), потому
что команда даже не знала, что эта HTTP-достижимая поверхность
существует. Ревью "пройти по каждому контроллеру и проверить
`@PreAuthorize`" — именно то, что делал LR-006 и каждый последующий
Architecture Pre-Check в этой сессии — структурно не может поймать
такой класс бага, потому что проверяет написанный код, не реально
достижимую HTTP-поверхность целиком.

**Long:** Spring Data REST — легитимный, активно поддерживаемый проект,
спроектированный для другого сценария: быстрые CRUD-прототипы, где
экспозиция по умолчанию — это фича, а не баг, отключение —
осознанный opt-out (`@RepositoryRestResource(exported=false)`,
`disableDefaultExposure()`), не opt-in. Архитектура этого приложения —
deny-by-default решения по каждой бизнес-операции — несовместима с
opt-out-экспозицией по конструкции. Причина дыры — не дефект ни в одном
компоненте по отдельности, а архитектурное несоответствие между ними.

**Когда именно прозевали (сводка):** на этапе выбора зависимостей при
scaffolding (Oct 2025, до содержательного кода) → не поймано на
Roundtable #1 (архитектурный ребилд с явными местами "Безопасность",
Jul 2026 — нашёл LR-006, точечный `@PreAuthorize`-пробел, не полный
аудит зависимостей) → не поймано ни одним последующим Architecture
Pre-Check (проверяют diff против ADR/слоёв, не полную поверхность
зависимостей) → не поймано ни одним прогоном `architect-reviewer` (тоже
ревьюит diff, не build.gradle целиком, пока diff его не касается) →
поймано впервые целенаправленным DevSecOps-аудитом (LR-022), заведённым
именно потому что в этой же сессии дважды нашлось "код выглядит
защищённым, никогда реально не проверялся" (LR-014, LR-020).

**Возможные последствия неустранённой дыры:**

- Подтверждено вживую: любой зарегистрированный аккаунт → полный ADMIN
  одним запросом.
- Зависимость жила с первых недель проекта — значит дыра была
  теоретически эксплуатируема весь срок работы прода, не только с
  момента обнаружения.
- Полный дамп расшифрованных PII (включая, вероятно, контакты
  несовершеннолетних участников через `Participant`-репозиторий),
  bcrypt-хэши, взламываемые offline, все финансовые записи.
- DSGVO: ровно тот сценарий "неавторизованный доступ к персональным
  данным детей", который триггерит обязательное уведомление о breach —
  серьёзная юридическая, не только техническая экспозиция для студии,
  работающей с детьми.
- Цепная реакция: получив ADMIN, атакующий получает полную внутреннюю
  видимость и мог бы использовать её для поиска других дыр (например,
  уже найденных в этом же аудите LR-024 teacher IDOR, LR-030 Group
  mass-assignment) — одна дыра как плацдарм для нахождения следующих.

### Часть 2 — Почему именно этот фикс правильный

**Это не "новейшее решение" в смысле новизны паттерна** — это старый,
десятилетиями устоявшийся принцип (attack surface reduction / least
functionality, ядро NIST SSDF и OWASP ASVS), применённый корректно.
Что действительно современно: сам класс уязвимости (неаудированный
авто-экспозирующий компонент фреймворка рядом с рукописным API) стал
встречаться чаще именно из-за AI-ассистированного scaffolding (точка
Wysopal выше) — поэтому защита (минимализм зависимостей, системный
аудит зависимостей, SBOM в CI) получила свежую актуальность, хотя сам
принцип не новый.

**Winch/Long:** современная Spring Security-рекомендация (Spring
Security 6.x, которую проект уже использует) — явная, method-level
авторизация как основная защита, URL-паттерны в `SecurityFilterChain`
как более грубый второй слой. Архитектура этого приложения уже
полностью следует этой рекомендации везде, **кроме** случайно попавшей
Spring Data REST-поверхности, которая через эту модель вообще не
проходила. Фикс не вводит новый паттерн — он убирает единственный
компонент, нарушавший паттерн, которому всё остальное приложение уже и
так следовало правильно.

**Почему удаление, а не переконфигурация — архитектурно правильный
выбор:**

- Spring Boot's `@ConditionalOnClass`-автоконфигурация: без зависимости
  на classpath уязвимый код физически не существует в работающей JVM —
  не "отключен", а структурно отсутствует. Ни один property, ни один
  будущий конфиг-файл, ни один случайный bean override не могут его
  воскресить.
- Переконфигурация (`config.disableDefaultExposure()`) оставила бы
  живую, latent мину: зависимость всё ещё на classpath, всё ещё часть
  supply chain, в одном minor-апгрейде Spring Boot или одном
  непроверенном merge conflict от повторной тихой экспозиции всего.
  "Невозможно по конструкции" — строго более сильный инвариант
  безопасности, чем "отключено конфигурацией".
- Подтверждено grep'ом перед удалением: ни одна строка кода проекта не
  использовала реальное поведение Spring Data REST
  (`@RepositoryRestResource`/`RepositoryRestConfigurer`) — зависимость
  несла ноль пользы при 100% риска. Не компромисс, чистая асимметрия.

**Задействованные зависимости:**

- Убрано: `spring-boot-starter-data-rest` (и транзитивно — Spring
  HATEOAS-контроллеры, ALPS/profile metadata эндпоинты — всё ушло вместе
  с ним).
- Добавлено для этого конкретного фикса: ничего.
- **Зеркальный случай в этой же сессии:** LR-020 (`spring-boot-starter-
  validation`) — обратная сторона той же дисциплины. Там реальная фича
  (`@Valid`) была нужна, но провайдер отсутствовал — пришлось
  **добавить** правильную минимальную зависимость. LR-020 и LR-023
  вместе показывают одну и ту же дисциплину, применённую симметрично в
  обе стороны: зависимости должны точно соответствовать тому, что
  реально используется — добавлять то, что действительно нужно, даже
  если его не хватало годами; убирать то, что не нужно, даже если оно
  было с первого дня.

**Более широкий архитектурный принцип:** это тот же принцип минимальной
поверхности атаки, применённый на уровне зависимостей, который
согласуется со всем остальным, что уже верно в security-архитектуре
этого приложения — deny-by-default `.anyRequest().authenticated()`,
stateless JWT с fail-fast проверкой секрета, AES-256-GCM field-level
шифрование без небезопасного fallback'а, явный `@PreAuthorize` на
каждом хендрайтен-контроллере. Фикс не вводит новую архитектурную
опору — он убирает единственный компонент, который молча работал
**вне** архитектуры, которой всё остальное уже правильно следовало,
восстанавливая архитектурную согласованность, а не изобретая новую.

### Синтез (Tech Lead)

Корневая причина — не единичная ошибка, а структурный слепой пятно
процесса: каждый уровень ревью в этом проекте (Architecture Pre-Check,
architect-reviewer, даже Roundtable #1's явные security-места) по
конструкции проверяет **написанный код против архитектуры**, а не
**полную HTTP-достижимую поверхность против дерева зависимостей**. Это
не повод переписывать существующий процесс — точечные ревью diff'ов
корректны и должны оставаться, — а повод добавить недостающий, отдельный
класс проверки: периодический (не разовый) аудит "что реально на
classpath и зачем", тот самый, который LR-022 впервые провёл и который
стоит повторять не только при следующем большом security-инциденте.
Дешёвый CI-guard, предложенный `architect-reviewer` при ревью фикса
(grep/dependency-assertion, чтобы `spring-boot-starter-data-rest` не
вернулся незаметно), — минимальная версия этой институционализации,
пока не заведён отдельным тикетом.

### Исходные данные (факты, не мнение)

### Часть 1 — Что именно мониторить (не просто "включить Actuator")

**Long:** Spring Boot Actuator + Micrometer — идиоматичный, first-class
способ, не костыль поверх логов. У проекта уже есть `spring-boot-
starter-actuator` (используется для `/actuator/health`) — не хватает
`micrometer-registry-prometheus` (даёт `/actuator/prometheus` в формате,
который `otelcol-contrib`'s `prometheus`-receiver ожидает нативно, тот
же формат, что уже проверен для numi) и осознанного выбора, какие
кастомные метрики завести, а не просто "что Micrometer даёт из коробки".

**Winch:** авторизационные решения должны быть видимы как метрика, не
только как лог-строка — лог теряется, тренд на дашборде замечают.
`GlobalExceptionHandler` уже сегодня — единственная точка, через которую
проходят `AuthorizationDeniedException`/`AccessDeniedException`,
`BadCredentialsException`, аккаунт-локаут (после фикса LR-026) — это и
есть естественная, минимальная точка инструментации: один counter на
каждый уже существующий `@ExceptionHandler`, ничего не размазывается по
сервисам.

**Moussouris:** метрики должны отвечать не на "жив ли сервис", а на
"кто-то сейчас пробует то, что мы уже один раз закрыли" — то есть
каждая находка LR-022 должна получить свой сигнал, не абстрактный
"security dashboard".

Конкретный набор (обвязка вокруг уже существующих точек в коде, не
новая архитектура):

| Метрика | Откуда | Что показывает |
|---|---|---|
| `auth_login_failure_total{reason}` | `GlobalExceptionHandler.handleBadCredentials`/`handleAccessDenied`/лок-аут-хендлер (после LR-026) | credential stuffing, брутфорс — прямой ответ на M10 |
| `auth_login_success_total` | `AuthService.authenticate()` | baseline для аномалий |
| `auth_register_total` | `AuthService.register()` | всплеск регистраций — ранний сигнал перед атакой |
| `authz_denied_total{path,role}` | `handleAccessDenied`/`handleAccessDenied` (тот же хендлер, что уже есть) | попытки обратиться к чужому/админскому ресурсу — прямой ответ на H1 (teacher IDOR) и в целом на класс LR-023 |
| `http_unmapped_path_total{path}` | новый компонент — см. Часть 3 | **ретроспективно самый ценный**: если бы это существовало 2025-10-21..2026-08-06, `GET/PATCH /users`, `/participants` (вне `/api/v1/**`) были бы видны как аномалия с первого дня, не через 9.5 месяцев |
| `backup_job_last_success_timestamp` | Postgres backup CronJob (LR-003) | закрывает уже известный, отдельный пробел — алертинг на бэкап |

**Wysopal:** важное ограничение честности — метрики не заменяют фиксы
LR-024..030, они делают эксплуатацию **видимой**, если она случится, и
сокращают время обнаружения с "9.5 месяцев, пока кто-то не закажет
аудит" до "минуты, пока дашборд не мигнёт". Не путать observability с
security — это соседние, не взаимозаменяемые слои.

### Часть 2 — Сетевая модель: почему это не отдельная задача от NetworkPolicy

**Mackey:** централизованная модель VM600 (project-VM не пушит сама,
VM600 сама скрейпит) — та же логика, что supply-chain-минимализм:
секрет Grafana Cloud токена живёт **в одном месте** (VM600), не
размножается по каждому проекту. Для LR это означает: `/actuator/
prometheus` не должен быть достижим ни для кого, кроме VM600.

**Winch:** это прямо тот же принцип, что обосновал удаление Spring Data
REST в LR-023 — "невозможно по конструкции" сильнее "закрыто
конфигурацией". Правильная реализация — не `@PreAuthorize` на
метрика-эндпоинте (это всё ещё "закрыто конфигурацией", тот же класс
хрупкости), а структурная сетевая изоляция:

1. `management.server.port` — отдельный порт (по образцу numi's `9090`),
   **не тот**, что слушает бизнес-API.
2. Этот порт не публикуется через k3s `Service`/`Ingress` вообще — он
   существует только внутри пода/namespace.
3. `NetworkPolicy` в `lr-dev` (тот самый нереализованный пункт из
   `INFRA-LR.md` §8 и M4 из аудита) — разрешает ingress на этот порт
   **только** с IP VM600 через сегмент `10.10.10.0/24`.

Реализация этого мониторинга — не побочный эффект, а прямая, естественная
**причина** наконец закрыть M4 (NetworkPolicy) и M7 (Actuator на
публичном listener'е) — нельзя правильно подключить VM600, не сделав
и то, и другое одновременно. Роадмап не откладывает эти находки на
"когда-нибудь" отдельным тикетом — он делает их предусловием для
самого мониторинга.

### Часть 3 — "Правильный", не дешёвый CI-guard

**Заказчик спросил конкретно, вписывается ли CI-guard в роадмап — да,
но не тот, что предлагался изначально.**

**Winch:** grep на строку `spring-boot-starter-data-rest` в `build.gradle`
— хрупкая проверка: ловит только этот один, уже известный случай. Другая
зависимость с тем же классом поведения (авто-экспозиция) — например,
если кто-то добавит Spring Boot Admin, или другой auto-configuring
starter, — пройдёт мимо неё незамеченной. Правильная проверка — не имя
зависимости, а **факт**: тестировать реально смонтированную HTTP-
поверхность против allow-листа, тем же способом, что уже доказал себя
в `SpringDataRestExposureTest` (LR-023), но обобщённо, не точечно под
один случай.

**Long:** механизм для этого уже есть в Spring без новых зависимостей —
`RequestMappingHandlerMapping.getHandlerMethods()` возвращает полный
реестр всех замонтированных `@RequestMapping`. Тест, который поднимает
контекст, читает этот реестр и утверждает "каждый путь либо начинается
с `/api/v1/`, либо явно в allow-листе (`/actuator/health`, ...)" — ловит
**весь класс** "что-то незаметно замонтировало HTTP-поверхность вне
нашего API", а не конкретно Spring Data REST. Это и есть источник
метрики `http_unmapped_path_total` из Части 1 — та же логика, реализованная
дважды: один раз как CI-тест (ловит на этапе сборки), один раз как
runtime-метрика (ловит, если что-то всё же проскочило CI, или если кто-то
целенаправленно пробует случайный путь в проде).

**Moussouris:** это и есть институционализация, о которой шла речь в
синтезе Roundtable #4 — не "не забыть про одну находку", а структурный
guard, переживающий любую конкретную находку.

**Mackey:** к этому же слою — SBOM, не разово. `./gradlew dependencies`
как артефакт каждого CI-прогона (или лёгкий CycloneDX Gradle-плагин,
не обязательно сразу полноценный SCA-инструмент) — минимальная версия
"что реально на classpath и зачем" как живой, а не разовый вопрос.

### Синтез (Tech Lead) — фазированный план

**Фаза 0 — Уже открытые находки LR-022 (предусловие, не часть этого
роадмапа как такового).** LR-021, LR-024..LR-030. Без чистой базовой
линии метрики будут показывать шум от уже известных дыр, не новых
попыток — есть смысл закрыть H1-H5/M1/M11 до или параллельно с Фазой 1.

**Фаза 1 — Observability-фундамент в самом приложении (полностью
делаемо сейчас, без внешней инфры):**
1. `micrometer-registry-prometheus` в `build.gradle`, `/actuator/
   prometheus` в `management.endpoints.web.exposure.include`.
2. Кастомные counter'ы из таблицы Части 1, инструментированные в
   `GlobalExceptionHandler` (существующие хендлеры) + `AuthService`.
3. `http_unmapped_path_total` — обобщённый фильтр/интерцептор,
   считающий запросы, не попавшие ни под один `@RequestMapping` внутри
   `/api/v1/**` и не в allow-листе статики/actuator.
4. `management.server.port` — отдельный порт, не публикуемый через
   k3s Service.
5. Регрессионный CI-тест на allow-лист путей (обобщение
   `SpringDataRestExposureTest`, Часть 3) — вписывается сюда, не как
   отдельная задача.

**Фаза 2 — Сетевая изоляция (требует инфра-доступа, частично не
делаемо мной):**
6. `NetworkPolicy` в `lr-dev`, ограничивающая ingress на новый
   management-порт только с IP VM600 (закрывает M4).
7. Подтверждение, что CNI кластера (flannel, по `INFRA-LR.md`) реально
   энфорсит `NetworkPolicy` — не предполагать, проверить (тот же урок,
   что уже стоил времени с Litestream/numi-nat.service —
   "active/сконфигурировано" ≠ "реально работает").

**Фаза 3 — Подключение к VM600 (гейтится на провижининге самой
VM600 — сегодня "заявлена, не развёрнута", INFRA-008, не в скоупе
одного этого проекта):**
8. LR ("tlab29") — новый `scrape_configs`-джоб в едином
   `otel-collector-config.yaml` на VM600, тот же формат, что у numi.
9. Дашборд в Grafana Cloud — request-rate/error-rate (как у numi) +
   новые security-панели из таблицы Части 1.
10. Alerting rules (ещё не построены даже для numi — общий, переиспользуемый
    паттерн для обоих проектов, не дублируется): всплеск
    `auth_login_failure_total`, любой ненулевой `authz_denied_total` на
    admin-only путях, любой `http_unmapped_path_total` > 0 (в норме
    должно быть строго ноль), падение backup-job'а.

**Фаза 4 — Институционализация процесса (без чего роадмап — разовый
всплеск, а не структура):**
11. Периодический (не разовый) повтор полного 3-фазного аудита
    (backend/infra/frontend) — календарный, не только "после следующего
    инцидента". LR-022's Фаза 6 (финальная верификация после закрытия
    Фазы 0) — первый инстанс этого повторяющегося процесса, не разовая
    галочка.
12. SBOM как CI-артефакт (Mackey, Часть 3).

**Контекст будущего использования, почему не откладывать на "когда
понадобится":** архитектурно предусмотренные, но пока не живые роли
`TEACHER`/`BUSINESS_OWNER` (LR-ADR по итогам Круглого стола #3) сегодня
не создают реальной IDOR-угрозы просто потому, что реальных сторонних
преподавателей ещё нет — весь риск H1 (teacher IDOR) сегодня чисто
теоретический для одного владельца-администратора. В момент, когда эти
роли реально оживут (несколько независимых учителей с реальным
доступом), тот же класс находок перестаёт быть теоретическим и
становится ежедневным риском — `authz_denied_total`-мониторинг должен
быть уже на месте **до** этого расширения ролей, не после первого
инцидента с ним. То же самое верно для реальной оплаты (LR-017,
Stripe/Numi) — платёжный трафик радикально поднимает ставки для всего,
что здесь предложено.
