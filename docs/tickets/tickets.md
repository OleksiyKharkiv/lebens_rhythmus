## LR-018 — Bootstrap первого админа: только через ручной psql, нет env-var/seed-механизма

**Tier:** LOW (dev-ops/onboarding gap, не риск для существующих данных)
**Статус:** Open · backlog, не блокирует ничего
**Источник:** вопрос заказчика "как сделать юзера админом" 2026-08-06

`PUT /users/{id}/role` (`UserController.java:158`) и admin-UI
(`admin/users/+page.svelte`) корректно реализуют смену роли — но оба
требуют `hasRole('ADMIN')`, то есть работают только когда админ уже
существует. Самый первый админ на чистом окружении (новый staging,
DR-восстановление, локальная разработка) сегодня назначается только
прямым `UPDATE users SET role = 'ADMIN' WHERE email = ...` через
`kubectl exec` в Postgres-под — ручная, недокументированная в коде
операция (описана только в истории чата/CHANGELOG, не в runbook).

**Направление** (не решено окончательно, требует выбора заказчика):
- Env-var-gated bootstrap при старте приложения: если `role=ADMIN`
  юзеров в БД ноль и задан `BOOTSTRAP_ADMIN_EMAIL` — повысить этого юзера
  (если уже зарегистрирован) при старте `main()`/через `ApplicationRunner`.
  Не создаёт юзера с нуля (пароль не через код) — только повышает роль
  уже существующему аккаунту, что проще и безопаснее.
- Альтернатива попроще: просто задокументировать текущую psql-команду в
  `docs/runbooks/` (bootstrap-checklist для нового окружения) — не менять
  код вообще, если механизм psql устраивает как разовая операция.

**Не начинать реализацию без:** решения заказчика, какой из двух путей
нужен (код vs документация) — второй вариант дешевле и, возможно,
достаточен на этом масштабе проекта (один owner, редкие новые окружения).

## LR-017 — Механизм подтверждения участия/оплаты (М2/М3 зависят от этого)

**Tier:** MED (продуктовое решение с архитектурными последствиями,

**Не начинать реализацию без:** явного решения заказчика по конкретному

## LR-003 — Бэкапы и репликация PostgreSQL (`lr-postgres`)

**Tier:** INFRA
**Статус:** Interim-решение готово в коде (Helm), **не применено на
кластере** — блокер на пользователе (см. "Осталось сделать" ниже).
**Срок применения interim-решения: 2026-08-05** (создать IDrive e2
bucket/credentials, задеплоить, провести реальный тест бэкапа —
пункты 1-4 чек-листа ниже; п.5 restore — тоже до этой даты, если
получится). Финальное решение (backup-контроллер) — отдельно, near-term,
привязано к апгрейду домашнего сервера (план — сентябрь 2026).
**Источник:** калибровочная сессия 2026-07-20; interim-реализация 2026-07-24;
срок 2026-08-05 назначен заказчиком 2026-07-24

Решение по обоим блокирующим вопросам получено от заказчика 2026-07-24:
хранилище — **IDrive e2** (тот же провайдер, что у numi Litestream,
отдельный bucket/credentials), механизм — **Kubernetes CronJob** (не
systemd на VM200/lr700, как изначально предполагал тикет — идиоматичнее
для k3s-хостящегося Postgres).

**Реализовано** (`devops/helm/lr-app/`):
- `templates/postgres-backup-cronjob.yaml` — CronJob `lr-postgres-backup`,
  `postgres:16-alpine` (уже содержит `pg_dump`), `restic` ставится на
  лету через `apk` (не заводить отдельный кастомный образ ради
  временного решения). `concurrencyPolicy: Forbid` +
  `activeDeadlineSeconds: 1800` — зависший прогон не блокирует
  расписание навсегда.
- `templates/postgres-backup-configmap.yaml` — сам скрипт (`pg_dump` →
  `restic init` (no-op если уже есть) → `restic backup` → `restic forget
  --prune`, retention 14 daily / 8 weekly).
- `values.yaml`: секция `postgresBackup` (schedule, repository, retention)
  + документация нужного `kubectl create secret lr-backup-secrets`
  (restic-password/access-key-id/secret-access-key — по той же конвенции,
  что `lr-backend-secrets`).
- **Проверено вживую** (не на проде — Docker-контейнер `postgres:16-alpine`
  локально): `pg_dump`/`restic` оба доступны и работают в этом образе;
  реальный прогон script'а против тестовой БД — `pg_dump` → `restic init`
  → `restic backup` → `restic forget --prune` — все шаги отработали
  успешно, снапшот реально создан. `helm template` — 0 ошибок, ConfigMap
  и CronJob рендерятся корректно, `enabled: false` корректно убирает оба
  ресурса.
- Процедура восстановления добавлена в
  `docs/runbooks/infra-fix-shutdown.md` — **ни разу не проверена на
  реальном кластере**, тот же урок, что уже был у numi/Litestream
  (бэкап без проверенного восстановления не доказан рабочим) — первый
  реальный прогон восстановления должен случиться при первой
  возможности, не откладывать.

**Осталось сделать (не может быть сделано мной — реальная прод-инфра):**
1. Создать bucket в IDrive e2 для LR (отдельный от numi).
2. `kubectl -n lr-dev create secret generic lr-backup-secrets ...` (см.
   `values.yaml` комментарий) — реальные credentials, не для передачи в
   чат.
3. Указать `postgresBackup.repository` в `values.yaml` (реальный
   bucket-URL) и задеплоить (`helm upgrade`).
4. Хотя бы один раз проверить `kubectl get cronjob`/`kubectl logs`, что
   первый реальный прогон в проде действительно создал снапшот в IDrive e2.
5. Прогнать restore-процедуру хотя бы раз (не обязательно поверх прод-БД
   — можно в тестовом namespace) — см. новый раздел в
   `infra-fix-shutdown.md`.

**Follow-up, найдено architect-reviewer 2026-07-24 (не блокирует, но не
забывать):**
6. Backup-job переиспользует `lr-db-credentials` (полные права владельца
   БД) — для `pg_dump` достаточно read-only роли. Отдельной роли в
   проекте нет нигде, создание требует ручной `psql`-сессии против
   прод-БД. Не блокирует запуск, но стоит сделать до серьёзного аудита
   TOM/DSGVO.
7. Нет алертинга при падении ночного backup-job'а — узнать можно только
   `kubectl get cronjob`/`kubectl logs` вручную. Отдельная, б о́льшая
   задача (интеграция с Grafana/мониторингом), не в скоупе interim-решения.

## LR-004 — Self-scoped payment history (`GET /api/v1/payments/me`)

**Tier:** MED (личный дашборд, LR-ADR-016) — не HIGH: не меняет
инвойс/платёжную запись, только читает по собственному `userId` из JWT.
**Статус:** Closed 2026-07-23
**Источник:** сессия 2026-07-22/23, построение личного дашборда

До этого изменения `PaymentController` не имел ни одного маршрута, доступного
обычному пользователю — все методы требовали `ADMIN`/`BUSINESS_OWNER`, что
блокировало требование "история платежей" личного дашборда (LR-ADR-016).

**Сделано:**
- `PaymentController.getMyPayments()` — `GET /api/v1/payments/me`,
  `@PreAuthorize("isAuthenticated()")`, `userId` берётся из JWT через
  `JwtAuthUtils.extractUserId()`, не принимается от клиента — исключает
  IDOR по конструкции (нет параметра `userId` для подмены).
- `PaymentService.getMyPayments(userId)` + `PaymentRepository
  .findByUserIdOrderByCreatedAtDesc(userId)` (тот же паттерн, что уже
  использовался в `EnrollmentRepository`).
- Найден и исправлен попутный баг в `SecurityConfig`: `GET
  /api/v1/activities/**` и `/api/v1/performances/**` не были в whitelist
  (только `/workshops/**`) — это 401'ило бы только что построенные
  публичные страницы каталога для любого анонимного посетителя.
- Тест `PaymentControllerTest` (`@WebMvcTest` + `spring-security-test`'s
  `jwt()` mock) — покрывает и happy path (пользователь получает свои
  платежи), и unauthenticated-запрос (401). Оба ревью-approve-условия
  architect-reviewer закрыты.

**Продуктовый вопрос про `note` — решён заказчиком (2026-07-23):** поле
`PaymentResponseDTO.note` (документировано как "optional refund reference or
note") **скрыто** от self-view — заведён `PaymentMapper.toSelfViewDTO()`,
используется только в `/payments/me`; admin-эндпоинты (`getAll`/`getById`)
по-прежнему используют `toResponseDTO()` с `note` как есть. Обоснование:
данных о том, что `note` реально используется как customer-facing поле, нет
(комментарий в коде — "admin/accounting reference"), значит по умолчанию —
не раскрывать, пока не появится осознанное решение сделать его
клиент-ориентированным (тогда — отдельное поле, не расширение смысла этого).
Покрыто `PaymentMapperTest` (2 теста: self-view без note, admin-view с note).
