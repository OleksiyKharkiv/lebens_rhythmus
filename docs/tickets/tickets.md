## LR-013 — Настроить реальные Brevo SMTP-креды для email-верификации

**Tier:** HIGH (auth-flow, но сама работа — чисто конфигурация)
**Статус:** Open · **блокирует реальную отправку писем** (регистрация уже
работает, аккаунт создаётся, но письмо с подтверждением никуда не уходит
без этого)
**Источник:** фича email-верификации, 2026-08-04

Код готов и покрыт тестами (32/32, см. `CHANGELOG.md`), но
`SMTP_USERNAME`/`SMTP_PASSWORD` сейчас пустые дефолты — отправка письма
падает (перехвачено, не роняет регистрацию, но письмо реально не уходит).

**Нужно (не может быть сделано мной):**
1. Создать в Brevo либо новый sender/domain для LR (`tlab29.com`), либо
   переиспользовать существующий numi-аккаунт с отдельным sender —
   решить, что проще/правильнее.
2. Получить SMTP-креды (host уже `smtp-relay.brevo.com`, порт 587).
3. Задать `SMTP_USERNAME`/`SMTP_PASSWORD` — добавить ключи `smtp-username`/
   `smtp-password` в существующий Secret `lr-backend-secrets`
   (`kubectl -n lr-dev edit secret lr-backend-secrets` или пересоздать с
   доп. `--from-literal`), **затем** добавить соответствующие
   `env:` записи (`secretKeyRef`) в `backend-deployment.yaml` — **в этом
   порядке, не наоборот**: если сначала добавить `secretKeyRef` на
   несуществующий ключ секрета, под уйдёт в `CreateContainerConfigError`
   (тот же класс бага, что уже ловили с `lr-backend-secrets`/
   `lr-backup-secrets` в этой сессии). Не присылать креды в чат.
4. Проверить `MAIL_FROM_ADDRESS` (дефолт `noreply@tlab29.com`) — домен
   должен быть верифицирован в Brevo (SPF/DKIM), иначе письма попадут в
   спам или не уйдут вовсе (тот же класс проблемы, что уже был у numi —
   "Brevo sender domain must be verified").
5. После настройки — зарегистрировать тестовый аккаунт, убедиться, что
   письмо реально приходит, ссылка работает.

**Также нужно (отдельное ручное действие, не блокирует эту фичу, но
срочно из-за отдельного бага):** удалить один тестовый аккаунт с
незашифрованным `first_name` в проде — см. LR-011 checklist.

## LR-014 — `resendVerification`: timing side-channel палит существование аккаунта

**Tier:** LOW (низкоценная цель для атаки, не платёжные/детские данные)
**Статус:** Open · backlog, не блокирует ничего
**Источник:** architect-reviewer, ревью email-верификации, 2026-08-04

`POST /auth/resend-verification` всегда возвращает 200 без тела
независимо от исхода — специально, чтобы не палить, существует ли
аккаунт/подтверждён ли он. Но реальное **время ответа** отличается: для
неизвестного/уже-подтверждённого email — почти мгновенно (один
`findByEmail` без побочных действий); для реального неподтверждённого
аккаунта — генерация токена + запись в БД + **синхронный** SMTP-коннект
к `smtp-relay.brevo.com:587`. Это измеримый timing-канал, различающий
"этот email существует и не подтверждён" от остальных случаев.

Не блокирует — не платёжные/детские данные за этим логином сегодня, но
стоит поправить: либо отправлять письмо асинхронно (fire-and-forget/
лёгкая очередь), чтобы время ответа не зависело от ветки, либо добавить
искусственную минимальную задержку перед ответом в обоих случаях.

**Tier:** INFRA
**Статус:** Interim-решение готово в коде (Helm), **не применено на

привязано к апгрейду домашнего сервера (план — сентябрь 2026).
**Источник:** калибровочная сессия 2026-07-20; interim-реализация 2026-07-24;
срок 2026-08-05 назначен заказчиком 2026-07-24

Решение по обоим блокирующим вопросам получено от заказчика 2026-07-24:
хранилище — **IDrive e2** (тот же провайдер, что у numi Litestream,
отдельный bucket/credentials), механизм — **Kubernetes CronJob** (не
systemd на VM200/lr700, как изначально предполагал тикет — идиоматичнее
для k3s-хостящегося Postgres).

**Реализовано** (`devops/helm/lr-app/`):
- `templates/postgres-backup-cronjob.yaml` — CronJob `lr-postgres-backup`,
  `postgres:16-alpine` (уже содержит `pg_dump`), `restic` ставится на
  лету через `apk` (не заводить отдельный кастомный образ ради
  временного решения). `concurrencyPolicy: Forbid` +
  `activeDeadlineSeconds: 1800` — зависший прогон не блокирует
  расписание навсегда.
- `templates/postgres-backup-configmap.yaml` — сам скрипт (`pg_dump` →
  `restic init` (no-op если уже есть) → `restic backup` → `restic forget
  --prune`, retention 14 daily / 8 weekly).
- `values.yaml`: секция `postgresBackup` (schedule, repository, retention)
  + документация нужного `kubectl create secret lr-backup-secrets`
  (restic-password/access-key-id/secret-access-key — по той же конвенции,
  что `lr-backend-secrets`).
- **Проверено вживую** (не на проде — Docker-контейнер `postgres:16-alpine`
  локально): `pg_dump`/`restic` оба доступны и работают в этом образе;
  реальный прогон script'а против тестовой БД — `pg_dump` → `restic init`
  → `restic backup` → `restic forget --prune` — все шаги отработали
  успешно, снапшот реально создан. `helm template` — 0 ошибок, ConfigMap
  и CronJob рендерятся корректно, `enabled: false` корректно убирает оба
  ресурса.
- Процедура восстановления добавлена в
  `docs/runbooks/infra-fix-shutdown.md` — **ни разу не проверена на
  реальном кластере**, тот же урок, что уже был у numi/Litestream
  (бэкап без проверенного восстановления не доказан рабочим) — первый
  реальный прогон восстановления должен случиться при первой
  возможности, не откладывать.

**Осталось сделать (не может быть сделано мной — реальная прод-инфра):**
1. Создать bucket в IDrive e2 для LR (отдельный от numi).
2. `kubectl -n lr-dev create secret generic lr-backup-secrets ...` (см.

   чат.
3. Указать `postgresBackup.repository` в `values.yaml` (реальный

4. Хотя бы один раз проверить `kubectl get cronjob`/`kubectl logs`, что
   первый реальный прогон в проде действительно создал снапшот в IDrive e2.
5. Прогнать restore-процедуру хотя бы раз (не обязательно поверх прод-БД
   — можно в тестовом namespace) — см. новый раздел в
   `infra-fix-shutdown.md`.

**Follow-up, найдено architect-reviewer 2026-07-24 (не блокирует, но не
забывать):**
6. Backup-job переиспользует `lr-db-credentials` (полные права владельца

## LR-011 — Перед деплоем шифрования PII (2026-07-24): подтвердить безопасность миграции существующих данных

**Tier:** HIGH (DSGVO, риск потери доступа к данным при неверном деплое)
**Статус:** Почти закрыт — проверено на реальном кластере 2026-08-03
(см. ниже), ждёт одного ручного действия перед деплоем.
**Источник:** инвентаризация шифрования, 2026-07-24

Добавлено `@Convert(EncryptedStringConverter.class)` на
`User.{firstName,lastName,phone,address,city,zipCode}`,
`Teacher.{firstName,lastName,phone}`, `Participant.{firstName,lastName,phone}`
— подтверждено интеграционным тестом, что шифрование/расшифровка
работают корректно **для новых записей**.

**Не подтверждено и блокирует деплой:** если в живой `lr-dev` БД уже есть
реальные строки с открытым (не зашифрованным) значением в этих колонках,
после деплоя Hibernate попытается расшифровать старый plaintext как
`base64(IV+ciphertext)` — упадёт с ошибкой на первом же чтении такой
строки (не тихо, а с exception, но для затронутых пользователей это
означает "аккаунт не открывается").

**Перед деплоем нужно явно одно из двух:**
1. Подтвердить, что таблицы `users`/`teachers`/`participants` пока не
   содержат реальных данных (только тестовые/пустые) — тогда деплоить
   можно как есть.
2. Если данные реальные — написать и прогнать одноразовый скрипт
   ре-шифрования существующих plaintext-значений **до** переключения
   `@Convert` на прод (или в рамках миграции с явным разделением
   "старые/новые" строк).

**Дополнительный риск:** бэкап (LR-003) ещё не активен на кластере
(`postgresBackup.enabled: false`, ждёт создание IDrive e2 bucket) — если
что-то пойдёт не так при этом деплое, отката через бэкап нет. Либо
включить бэкап первым, либо действовать особенно осторожно.

**Follow-up, не блокирует:** `Participant.birthDate` — нативная колонка
`DATE`, текущий `EncryptedStringConverter` — только `String→String`,
нужен отдельный `LocalDate`-конвертер, если решат шифровать и дату
рождения тоже (сейчас — сознательно нет).

**Уже исправлено 2026-08-03 (та же ревью-волна, отдельные баги — не
блокировали именно эту миграционную задачу, но были реальными
регрессиями):**
- Поиск пользователей (`UserService.searchUsers`) был сломан шифрованием
  (`LIKE` по шифротексту) — переписан на decrypt-and-filter, тест добавлен.
- `VARCHAR(255)` мог переполниться после шифрования (особенно `address`,
  без ограничения длины) — `V2__widen_encrypted_pii_columns.sql` расширил
  затронутые колонки до `TEXT`.

**Основной блокер — проверено на реальном `lr-dev` 2026-08-03:**
```sql
SELECT (SELECT count(*) FROM users WHERE first_name IS NOT NULL) AS users_with_name,
       (SELECT count(*) FROM teachers) AS teachers_total,
       (SELECT count(*) FROM participants) AS participants_total;
-- 1 | 0 | 0
```
Реальных клиентских данных нет — `teachers`/`participants` пусты, в
`users` только один тестовый аккаунт (собственный, заказчика), но у него
`first_name` реально заполнен (не NULL) — значит он бы упал при первом
чтении после деплоя, это и есть тот самый сценарий, который тикет
описывает, просто в масштабе одной строки, не прод-данных клиентов.
**Решение заказчика:** удалить этот один тестовый аккаунт вручную перед
деплоем (не гонять инструмент ре-шифрования ради одной строки).

**Инструмент ре-шифрования построен и протестирован на будущее** —
`backend/src/main/java/com/be/tools/PiiReencryptionRunner.java`
(`@Profile("reencrypt-pii")`, полностью инертен при обычном запуске
приложения; dry-run по умолчанию, требует `--apply` для реальной записи;
идемпотентен — определяет уже зашифрованные строки попыткой реального
decrypt, не эвристикой по длине/формату; работает через raw JDBC, не
через JPA/`@Convert`, иначе сам процесс чтения legacy-строк упал бы
раньше, чем инструмент успел бы их обработать). Покрыт
`PiiReencryptionRunnerTest` — сеет смесь plaintext+уже-зашифрованных
строк напрямую в БД, проверяет: dry-run ничего не пишет, `--apply`
шифрует только plaintext (не трогает уже зашифрованное), обычное чтение
через repository после этого больше не падает. Полный тест-сьют (20
тестов) — зелёный. Пригодится, если в будущем реальные данные накопятся
до следующего похожего изменения схемы.

**Осталось перед деплоем:**
1. Удалить тестового юзера с `first_name IS NOT NULL` вручную (команды
   даны в чате 2026-08-03 — `SELECT` для подтверждения id, затем `DELETE`).
2. LR-003 (бэкап) всё ещё не активен на кластере — риск отсутствия отката
   остаётся, деплоить с осторожностью независимо от пункта 1.
