## LR-ADR-001 — Frontend: полный снос и перестройка, не поэтапная миграция

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Harris, Osmani)

**Контекст:** Текущий фронтенд — 18 статических страниц без фреймворка.
Реальное содержание, проверенное чтением исходника (не предположение):
главная страница — один экран (заголовок + абзац + 2 кнопки), About —
один блок с тематически не связанным фоновым изображением. Ни дизайн-
системы (0 CSS-переменных), ни видео/анимации, ни программ, ни галереи.

**Решение:** Не мигрировать существующие страницы поэтапно — строить
новый фронтенд с нуля на выбранном фреймворке (кандидат — Svelte, см.
LR-ADR "фреймворк не финализирован" ниже). MVP-периметр первой волны —
три страницы: презентация/Home, About, Login/Register (см. LR-ADR-010).

**Consequences:** Не нужно проектировать промежуточные состояния/
редиректы для 18 страниц сразу — упрощает работу. Требует полноценной
фазы UX-ресёрча (LR-ADR-009) прежде чем строить, не параллельно.

## LR-ADR-002 — Backend auth: полная перестройка + field-level шифрование чувствительных данных

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Johnson, Hunt, Schneier); подтверждено владельцем ("почти хардкод от AI-IDE")

**Контекст:** Текущая auth-конфигурация оценена владельцем как в
значительной части автосгенерированная AI-IDE, требующая глубокой
ревизии. Независимо найдено (см. `ARCHITECTURE_OLD.md` §4.3): JWT_SECRET
передаётся plaintext в Helm-манифесте, тогда как DB-пароль защищён
`secretKeyRef` — асимметрия в одном файле. Данных о детях/платежах пока
нет (3 тестовых аккаунта, все — семья) — окно для перестройки, пока цена
ошибки минимальна.

**Решение:** Полная перестройка механизма аутентификации/авторизации, не
патч поверх текущего. Одновременно — внедрение field-level шифрования
для чувствительных колонок (персональные данные, банковские реквизиты)
по требованиям GoBD/DSGVO, механизм — `AttributeConverter`/`@Convert` на
уровне JPA-колонки либо отдельный порт `EncryptionService` (граница
между этими двумя вариантами — открытый вопрос реализации, не
блокирует принятие решения).

**Consequences:** Осознанное дублирование модулей ради гибкости —
разрешено владельцем явно, если повышает читаемость/модульность (не
считать техдолгом по умолчанию). Владелец — единственный, кто имеет
доступ к кластеру сейчас (Russinovich) — снижает срочность "чужого
доступа", не снижает срочность качества решения.

## LR-ADR-003 — БД: пересоздание схемы с нуля + миграции, независимо от инфра-апгрейда

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Vogels, Momjian, Kerstiens, Hightower)

**Контекст:** Миграций нет (`ARCHITECTURE_OLD.md` §2.4 — `ddl-auto=update`
+ runtime ALTER-костыль `DatabaseFixConfig`). Владелец подтвердил: текущие
данные не имеют ценности ("можем всё сносить бульдозером"), объём данных
мал. Ожидаемый рост — скромный (~100 постоянных участников за год).

**Решение:** Не мигрировать существующую схему — пересоздать с нуля с
первой же миграцией как честный baseline (Flyway или Liquibase — выбор
инструмента не финализирован здесь). Это решение **не привязано** к
срокам инфраструктурного апгрейда (LR-ADR-006) — можно и нужно делать
сейчас.

**Consequences:** Снимает риск "миграция ломает прод-данные", поскольку
данных для сохранения по факту нет. Требует явного выбора Flyway vs
Liquibase — не сделано в рамках этого ADR.

## LR-ADR-004 — Новая роль "Преподаватель" как отдельный bounded context ("Faculty Management")

**Статус:** Accepted (направление) · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Evans)

**Контекст:** Владелец подтвердил задумку (не реализовано): преподаватели-
субподрядчики со своими программами должны получать усечённые права
администратора — создание расписания, состав групп (по времени, возрасту,
вместимости), резервирование помещений в общем графике лаборатории (два
арендованных зала, локация нестабильна — может меняться под конкретный
ивент). В коде уже существует частичный фундамент: роль `TEACHER` и
несколько read-эндпоинтов, скоуп-ленных по `teacherId`
(`/workshops/teacher/{id}`, `/groups/teacher/{id}`,
`/teacher/groups/{id}/participants`) — write-прав под это пока нет.

**Решение:** Не косметическая доработка роли `TEACHER` — полноценная
модель прав "преподаватель управляет только своими группами/расписанием,
не чужими", отдельный bounded context, не поле/флаг на существующих
сущностях. Точечная привязка зала к конкретному событию уже заложена
архитектурно (`Event.venue_id` отдельно от `Workshop.venue_id`,
подтверждено по коду) — не хватает UI, реализация модели данных не
требуется с нуля.

**Consequences:** Расширяет скоуп работы над `Group`/`Workshop` — эти же
сущности выбраны эталоном для LR-ADR-005 не случайно, а именно потому,
что сюда бьёт эта роль.

## LR-ADR-005 — Domain/persistence-разделение: точечное, не тотальное

**Статус:** Accepted (направление) · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Martin, Evans); `ARCHITECTURE_OLD.md` §5

**Контекст:** `ARCHITECTURE_OLD.md` §5.2 зафиксировал главное нарушение
гексагональной задумки — JPA-аннотации прошиты прямо в domain-классы.
Владелец подтвердил реальную операционную потребность (не эстетику):
возможность апдейтить/настраивать каждую сущность независимо, без
остановки всего проекта и без слома по цепочке половины кодовой базы —
но не для всех 17 сущностей сразу.

**Решение:** Не переписывать все 17 entity-классов одним марш-броском.
Выбрать `Group`/`Workshop` эталоном разделения domain/persistence (из-за
роли "Преподаватель", LR-ADR-004) — отработать паттерн на них, расширять
на остальные сущности по мере реальной необходимости, не превентивно.

**Consequences:** Формальных инвариантов уровня numi ARCH-1..4 у LR пока
нет (только устаревшая ERM-диаграмма) — этот ADR не заменяет их
написание, только задаёт направление первого шага.

## LR-ADR-006 — Инфра: два независимых таймлайна (схема/безопасность — сейчас, HA/бэкапы — осень)

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Hightower, Vogels, Momjian)

**Контекст:** Ранее неявно смешивались две разные шкалы времени: "апгрейд
домашнего сервера осенью" воспринимался как блокер для всей инфра-
работы. Владелец подтвердил: дата апгрейда нетвёрдая (окно
сентябрь-ноябрь), при этом текущая нагрузка/масштаб — минимальны.

**Решение:** Работа над схемой БД, миграциями и безопасностью
(LR-ADR-002, LR-ADR-003) **не ждёт** осеннего железа. HA, репликация,
бэкап-инфраструктура (LR-003 в `docs/tickets/tickets.md`) — привязаны к
реальному окну сентябрь-ноябрь, не раньше и не позже без явной причины.

**Consequences:** Разблокирует немедленный старт кодовой работы над БД,
не дожидаясь инфраструктурных решений.

## LR-ADR-007 — Модель угроз: приоритет автоматизированным атакам и крипто-гигиене

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Hunt, Schneier)

**Контекст:** Владелец явно определил реалистичного противника —
случайный бот-сканер портов **и** state-level actor, явно **не**
конкурент и **не** обиженный бывший участник.

**Решение:** Приоритизировать защиту от автоматизированного сканирования
(rate-limiting, стандартная защита от брутфорса) и криптографическую
гигиену (LR-ADR-002) выше, чем контроли против инсайдерской угрозы или
целенаправленного саботажа со стороны знакомых лиц.

**Consequences:** Не исключает инсайдерские риски полностью, но снимает
их с топ-приоритета при ограниченных ресурсах одного разработчика.

## LR-ADR-008 — Perf floor: поддержка слабых Android-устройств — non-negotiable

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Osmani)

**Контекст:** Целевая аудитория по устройствам — не только "средний
немец" (по формулировке владельца, "уже ниже среднего" по достатку), но
и пользователи на слабых Android-устройствах.

**Решение:** Performance-бюджет — обязательное требование к новому
фронтенду (LR-ADR-001) с самого начала проектирования, не
пост-оптимизация. Полный офлайн-функционал PWA — второй волной, не
первой (см. также LR-ADR-010), но производительность на слабом железе —
требование первой волны.

**Consequences:** Ограничивает выбор UI-библиотек/эффектов "эффектность
с разумным балансом ресурсов" — буквально формулировка Olena, теперь
закреплена как техническое ограничение, не пожелание.

## LR-ADR-009 — UX: ставка на непохожесть, отдельная фаза ресёрча

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Norman)

**Контекст:** Владелец сознательно отказался от референсов "сделайте как
у X" — ставка на непохожесть, полный собственный ресёрч фич, не
копирование чек-листа трендов. Аудитория — от подростков (регистрируют
по закону родители) до пожилых участников, оба конца спектра должны
быть впечатлены.

**Решение:** UX/визуальный дизайн — отдельная фаза работы до кодирования
UI, не "заодно с бэкендом". Источник конкретных предпочтений — опросник
Olena (`docs/product/olena-questionnaire.md`), не домыслы инженера.

**Consequences:** Требует времени на исследование до старта фронтенд-
кодирования (LR-ADR-001) — явно закладывать в роадмап, не сжимать.

## LR-ADR-010 — Продуктовый MVP-периметр: Home + About + Registration первыми

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Cagan)

**Контекст:** На прямой вопрос "какая одна вещь важнее всего через
полгода" владелец ответил: первая страница == презентация + "О нас" +
регистрация участников. Это совпало (независимо подтверждено чтением
кода) с тремя реально существующими сегодня страницами.

**Решение:** Первая волна нового фронтенда (LR-ADR-001) — именно эти три
страницы, не расширенный список 4.1-4.6 целиком. Личный кабинет/дневник
занятий — решает проблему одновременно админа и участников/родителей —
приоритет второй волны, не первой.

**Consequences:** Даёт чёткий, узкий скоуп для первого релиза нового
фронтенда — не "переписать все 18 страниц сразу".

## LR-ADR-011 — Маркетинг/AI: усиление личного присутствия Olena, не замена

**Статус:** Accepted · **Дата:** 2026-07-20 · **Источник:** Roundtable #1 (Godin, корректирует Enthusiast-Adventurer)

**Контекст:** На вопрос "что реально приводит новых участников" владелец
ответил: не "что", а "кто" — Olena лично. Первоначальная идея (полностью
автономный AI, пишущий посты в соцсети) — скорректирована.

**Решение:** AI/маркетинг-инструменты проектируются как усилители,
дающие Olena лёгкий способ быстро поделиться моментом (черновик поста по
фото/видео с занятия, с согласия) — не как автономная замена её
личного голоса.

**Consequences:** Сужает скоуп AI-интеграции в маркетинге относительно
первоначального максималистского предложения Phase 2 — не убирает
AI-инструменты, меняет их роль с "автопилот" на "ассистент".

## LR-ADR-013 — Аудитория по умолчанию: взрослые, язык DE→UA/EN (без RU)

**Статус:** Accepted · **Дата:** 2026-07-21 · **Источник:** Roundtable #1, Round 3 (анкета Olena)

**Контекст:** Гипотеза Phase 3 предполагала родителей как основную
аудиторию. Прямой ответ Olena: чаще всего сайт первым откроют **взрослые,
ищущие занятие для себя**, не родители. Язык по умолчанию — немецкий,
дополнительно должны быть доступны украинский и английский. Русский не
выбран ни в каком качестве, несмотря на то что схема уже несёт
`titleUa`/`titleEn` на `Activity`/`Group`.

**Решение:** Тон и порядок сообщения на главной странице проектируется
для взрослого, ищущего занятие для себя, не для родителя-посредника
(родительский сценарий остаётся поддержанным, просто не первичен). i18n —
DE (по умолчанию) → UA, EN (равнозначные вторые) — не добавлять `titleRu`
на `Activity`/`Group`.

**Consequences:** Меняет приоритет UX-копирайтинга (LR-ADR-009) — тексты
трогают чувства "я хочу для себя", не "я ищу занятие для ребёнка".

## LR-ADR-014 — Визуальное направление зафиксировано

**Статус:** Accepted · **Дата:** 2026-07-21 · **Источник:** Roundtable #1, Round 3 (анкета Olena)

**Контекст:** LR-ADR-009 постулировал отдельную фазу UX-ресёрча вместо
референсов. Anкета дала конкретный, не абстрактный набор координат:
характер — "элегантный, вдохновляющий, высокое искусство"; цвет — яркие
насыщенные "живые" цвета; шрифт — мягкий, дружелюбный, округлый (не
строгий деловой, не рукописно-театральный); движение — 1 из 5 (почти
статично); видео на главной — не нужно, фото достаточно. Референсов
сознательно нет ("самобытность") — подтверждено дважды (Round 1 Норману
и Round 3).

**Решение:** Это и есть направление для LR-ADR-001 (новый фронтенд) —
не искать более широкий мудборд, строить по этим четырём координатам
напрямую: элегантность + яркий цвет + мягкая типографика + почти полная
статика.

**Consequences:** Снижает нагрузку на perf-бюджет (LR-ADR-008) в части
видео/тяжёлой анимации — упрощает первую волну технически, хотя
perf-требование для слабых Android остаётся в силе для фото/шрифтов/
общего веса страницы.

на этапе MVP — привязывает `Activity` к Priority 1 в `lr-erm-2026-07.drawio`.

## LR-ADR-016 — Личный кабинет: минимальный скоуп, напоминания — отдельный канал

Дневник прогресса педагога и раздел напоминаний в кабинете — не выбраны.

Telegram (не push внутри приложения).

**Решение:** Личный кабинет первой волны — три раздела: расписание,
медиа, платежи. Напоминания реализуются как исходящая интеграция
(email/WhatsApp/Telegram), не как раздел UI кабинета. Дневник прогресса
педагога — не в скоупе первой волны, не отменён, отложен.

**Consequences:** Сужает и упрощает скоуп личного кабинета относительно
черновой гипотезы — быстрее в реализации. WhatsApp/Telegram-интеграция
для напоминаний становится отдельной технической задачей (не существует
в коде сегодня, требует нового адаптера).

## LR-ADR-021 — `Course` выделен в отдельную сущность, ERM-узел "Workshop/Course" расформирован

**Статус:** Accepted (ERM обновлён, реализация — по тикетам LR-065+) ·
**Дата:** 2026-08-09 · **Источник:** прямой запрос заказчика (Olena) —
срочная задача по странице "Курсы", юридически связанная с
`docs/compliance/tlab29-zfu-compliance-brief.md`

**Контекст:** на стадии проектирования (Roundtable #1, 2026-07-20)
`Course` и `Workshop` были ошибочно слиты в один ERM-узел
("Workshop/Course", `docs/architecture/erm.drawio`) — на абстрактном
уровне это оказались две различные сущности с разной семантикой:

| | Workshop | Course |
|---|---|---|
| Длительность | 1-2 дня (иногда до недели) | 1 месяц – 1 год, с возможной пролонгацией |
| Периодичность занятий | Марафон, 3-8ч/день подряд | 1-3 раза/неделю, по 1-2ч |
| Онлайн/оффлайн | Только оффлайн (по словам заказчика; лазейка для онлайн предусмотрена в коде) | Может быть онлайн, оффлайн или гибрид |
| Итог | Может завершаться Perfomance | Может включать периодические Workshop'ы и завершаться Performance |

Разделение подтверждено реальным кодом: `Workshop.java` не имеет
понятия периодичности/регулярности расписания вообще (только
`startDate`/`endDate` как единый диапазон) — механически расширить его
под курс-логику означало бы либо ломать существующую Workshop-модель,
либо городить условную ветвистую логику внутри одной сущности под два
разных жизненных цикла.

**Решение:**
- Новая сущность `Course` (`courses`), независимая от `Workshop`.
- `Workshop.courseId` — nullable FK на `Course` (zero-to-many: один
  Course может включать несколько Workshop'ов, каждый Workshop
  принадлежит максимум одному Course). Не многие-ко-многим — по
  формулировке заказчика ("курс включает воркшопы") связь
  однонаправленная, воркшоп не "живёт" одновременно в нескольких
  курсах.
- `Performance.courseId` — новая nullable FK на `Course`, добавлена
  **рядом** с уже существующей `Performance.workshopId` (не заменяет
  её) — Performance может завершать либо Course, либо один Workshop,
  либо ни то ни другое, независимо друг от друга.
- Собственная модель расписания/периодичности `Course` (как именно
  хранить "по Пн и Ср, 18:00-20:00, с 01.03 по 31.05") — **не решена
  этим ADR**, вынесена на отдельный круглый стол (`LR-065`, гейтит
  тикет создания `Course`-сущности) — несколько технически валидных
  подходов (RRULE-подобное хранение, простой массив дней недели,
  генерация реальных строк `Session` из паттерна), нужен осознанный
  выбор, не первое, что пришло в голову под давлением срока.

**Consequences:** `docs/architecture/erm.drawio` обновлён (узел
переименован в "Workshop", добавлены `Course`/`Session`, связи
`courseId` помечены пунктиром/оранжевым как "структура подтверждена,
детали Course.Session — нет", до результата `LR-065`). Реализация —
серия тикетов `LR-065`..(см. `tickets.md`), не один большой диф — риск
ошибиться в фундаментальной сущности слишком высок, чтобы делать это
одним нерецензируемым куском.

## LR-ADR-022 — Мульти-день расписание: новая сущность `Session` под `Group`, не отдельный `Group` на день

**Статус:** Accepted (ERM обновлён, реализация — LR-066) · **Дата:** 2026-08-09
**Источник:** тот же запрос заказчика, п.4 (форма создания Воркшопа)

**Контекст:** заказчик попросил заменить единственную пару `Start`/`Ende`
в форме создания Воркшопа на "Количество дней" → N под-форм, каждая со
своими `Start`/`Ende`/`Место проведения`. Два технически валидных
способа реализации: (а) каждый день — отдельный `Group` (переиспользует
существующую сущность), (б) новая дочерняя сущность `Session` внутри
одного `Group`.

Ключевой аргумент против (а): `Group.enrollments` — участники
регистрируются на конкретный `Group`. Если каждый день многодневного
воркшопа — отдельный `Group`, участник должен регистрироваться
**отдельно на каждый день** — это не соответствует реальному сценарию
"один билет на весь 3-дневный воркшоп-марафон".

**Решение:** новая сущность `Session` (`group_sessions`), `@ManyToOne`
на `Group`, поля: `startDateTime`, `endDateTime`, `venue` (своя FK на
`Venue`, не общая с `Group.venue` — как раз то, что запросил заказчик:
разные дни могут проходить в разных местах). `Group.startDateTime`/
`endDateTime`/`venue` остаются как есть (для одно-дневных
Group — большинство существующих данных) — многодневный случай
дополнительно получает `Session`-записи, не заменяет старые поля
целиком (нет breaking change для уже существующих одно-дневных Group).
`Group.enrollments`/`capacity` остаются на уровне `Group` — один список
участников на весь многодневный Group, независимо от числа `Session`.

**Consequences:** та же `Session`-сущность используется и в форме
создания Воркшопа (макс. 10 дней подряд, п.4 заказчика), и потенциально
переиспользуется для `Course`, если `LR-065`-круглый стол решит, что
Course тоже нужны материализованные записи отдельных занятий (не
предрешено этим ADR).

## LR-ADR-023 — Модель расписания/периодичности `Course`: `Group` несёт правило повторения, `Session` материализует занятия

**Статус:** Accepted (реализация — LR-069+) · **Дата:** 2026-08-09
**Источник:** Roundtable #8 (`docs/decision-history/roundtable-log.md`),
рецензировано `architect-reviewer` (правки внесены в протокол до
формализации этим ADR) · закрывает вопрос, явно отложенный
`LR-ADR-021`

**Контекст:** `LR-ADR-021` выделил `Course` в отдельную сущность, но не
решил, как хранить его регулярность занятий ("по Пн и Ср, 18:00-20:00,
с 01.03 по 31.05"). Панель (Fowler — паттерн recurring-events; Vernon —
границы агрегатов; McGrane — content-as-data/ZFU; Long — Spring/JPA)
рассмотрела вопрос против уже доказанного в проекте прецедента
`Workshop → Group` (`LR-015`) и уже реализованной `Session`
(`LR-ADR-022`/`LR-067`).

**Решение:**
1. `Course` остаётся чисто описательной сущностью: `titleDe/En/Ua`,
   `descriptionDe/En/Ua`, `ageGroupId`, булевы флаги
   `isOnline`/`isSynchronous`/`hasRecordings`, мультиязычное
   `formatDisclaimerDe/En/Ua` (единый источник ZFU-текста для сайта и
   переписки с ведомством). **Без единого поля расписания** — то же
   разделение ответственности, что уже действует для `Workshop`.
   "Только для взрослых" и "без сертификата/диплома" — намеренно
   свободный текст внутри `formatDisclaimer` (нет противоречивого
   UI-состояния, которое стоило бы структурно блокировать, в отличие от
   `hasRecordings`), не отдельные булевы поля.
2. `Group` расширяется: `courseId` (nullable, рядом с существующим
   `workshopId`; ровно один из двух задан — см. п.4 ниже),
   `recurrenceDaysOfWeek`/`sessionStartTime`/`sessionEndTime`
   (используются только при заданном `courseId`). Диапазон дат курса —
   существующие `Group.startDateTime`/`endDateTime` (первая/последняя
   дата генерации), `endDateTime` обязателен для Course-группы (в
   отличие от опционального у Workshop-группы). Одна `Group` = одна
   вместимость/список участников на весь курс, независимо от числа
   занятий — тот же принцип, что `LR-ADR-022`.
3. `Session` (`LR-067`) переиспользуется без изменения структуры:
   `SessionService` получает новый метод генерации `Session`-строк из
   правила повторения `Group` на каждую подходящую дату в диапазоне.
   Регенерация запускается **только** при реальном изменении полей
   правила (дни недели/время/диапазон дат), не при любом сохранении
   `Group` — explicit guard в `GroupService`, не побочный эффект каждого
   save. Существующий `replaceSessionsForGroup` — деструктивный
   clear+re-add (подтверждено `SessionIntegrationTest` на реальном
   Postgres); при повторной регенерации ручные правки отдельных
   `Session` (перенос одного занятия и т.п.) будут потеряны — принятый
   trade-off для этого масштаба (не полное соответствие
   Fowler-паттерну "occurrence независимо редактируем без разрушения
   правила"), административный UI (`LR-074`/`LR-075`) обязан явно
   предупреждать об этом перед регенерацией.
4. `GroupService.createGroup`/аналог обязаны валидировать mutual
   exclusivity `workshopId`/`courseId` explicitly (проверка "ровно один
   задан") — сегодня это непроговорённая конвенция без enforcement ни
   на уровне БД, ни на уровне сервиса, для `Workshop.courseId`/
   `Performance.courseId` (`LR-ADR-021`) тоже.
5. **Отдельный обязательный follow-up** (не входит в реализацию самого
   `Course`, блокирует Course-регистрацию): `Enrollment.workshop`
   сегодня `@ManyToOne(optional = false)`. Нужен: `workshop` → nullable
   + новое nullable `course`-поле; `EnrollmentService` — новый путь
   регистрации на Course (текущий `enroll(workshopId, ...)` выводит
   `PENDING`/`CONFIRMED` из `workshop.getPrice()`, у `Course` цены нет
   в этой модели — нужно отдельное решение о цене/статусе);
   `EnrollmentController` — новый route; `Order` — тот же
   workshop-only-FK паттерн, тот же пробел, если появятся платные
   Course; `uk_user_workshop` — не защищает от дублей после того, как
   `workshop_id` станет nullable (Postgres не считает `NULL` дубликатом
   в unique-constraint), нужен app-level guard или параллельный
   constraint для Course.

**Не выбрано и почему:** RRULE-подобное хранение (мощь не нужна под
масштаб "1-3 раза/неделю, макс ~150 занятий/курс" — оверинжиниринг);
отдельная от `Group`/`Session` параллельная структура специально для
Course (дублирование уже доказанного паттерна без причины); хранение
compliance-текста как свободного описания без структурных флагов (не
решает риск разъехаться с письмом в ZFU, просто переносит его).

**Consequences:** `docs/architecture/erm.drawio` обновлён — снята
пометка "TBD" на `Course`, добавлена связь `Group↔Course` (nullable
`courseId`). Реализация разбита на тикеты: расширение `Group` (миграция
+ новые поля), генерация `Session` из паттерна в `SessionService`,
mutual-exclusivity guard в `GroupService`, и отдельным тикетом —
`Enrollment`/`EnrollmentService`/`EnrollmentController`/`Order`-пробел
из п.5 (см. `tickets.md`).
