## ⚡ ARCHITECTURAL PRE-CHECK (выполнять перед каждым кодовым решением)

Перед тем как написать или предложить любой код, Claude обязан явно пройти
следующий чеклист и кратко изложить результат в виде блока
**"Architecture Pre-Check"** прямо перед кодом.

### 1. Слой и направление зависимостей

Проверить, что предлагаемое решение не нарушает инварианты
(PROJECT_INDEX.md §5):

```
controller/ → service/ → repository/ (Spring Data JPA) → entity/
```

- `entity/` — JPA-сущности. Никакой бизнес-логики сверх простых инвариантов
  (например, статус-переходов на уровне объекта). Не знает о DTO, HTTP.
- `service/` — бизнес-логика, транзакционные границы (`@Transactional`).
  Не знает о `HttpServletRequest`/`ResponseEntity` напрямую.
- `controller/` — parse (`@RequestBody`) → validate (`@Valid`) → call
  service → respond (`ResponseEntity`). Никакой бизнес-логики.
- `repository/` — только Spring Data JPA интерфейсы (или `@Query`), никакой
  бизнес-логики.

**Красные флаги (нарушение → объяснить почему и предложить правильный слой):**
- Controller делает запрос через `EntityManager`/`JdbcTemplate` напрямую
- Service возвращает `ResponseEntity` или знает про HTTP-статусы
- Entity содержит бизнес-правила сложнее простых инвариантов состояния
- Новый тип добавлен в `entity/` только потому что "удобно"
- `DatabaseFixConfig`-подобный паттерн (миграция логики через код при
  старте приложения вместо SQL-миграции) — см. DEBT-1 в PROJECT_INDEX.md,
  не повторять этот паттерн для новых изменений схемы

### 2. Расширяемость и мутабельность

Ответить на вопрос: **если через 6 месяцев это нужно будет изменить, сколько
файлов затронет изменение?**

**Правила (пока черновик — уточнять по мере реальных прецедентов):**
- Новый тип занятия/активности → должен добавляться данными
  (строка в таблице `activities`), не новым enum-значением в коде, если
  возможно избежать пересборки при добавлении нового вида занятий.
- Новая роль пользователя → расширение существующей ролевой модели
  Spring Security, не отдельная параллельная система прав.
- Новый способ оплаты (если появится) → адаптер под общий интерфейс, не
  хардкод в сервисе бронирования.

### 4. Datenschutz-check (персональные данные — MANDATORY если диф трогает
пользователей, детей-участников, оплату)

> ⚠️ Черновик-чеклист, НЕ подтверждённое юридическое требование — см.
> PROJECT_INDEX.md §9. Работает как сигнал "здесь нужна осторожность",
> реальную формализацию делать с юристом.

Для любого кода, касающегося таблиц с персональными данными
(`users`, участники/студенты, если появятся):

- Поле содержит данные ребёнка (ФИО, дата рождения, фото) или данные
  опекуна (контакты)? Если да — отметить явно в PR/тикете.
- Поле содержит данные о здоровье (аллергии, ограничения для физической
  активности)? Это Art. 9 DSGVO — специальная категория, повышенная
  защита. Явно отметить, не добавлять "по умолчанию" без обсуждения.
- Если добавляется новое поле с персональными данными — нужно ли
  шифрование на уровне приложения, или достаточно существующих мер
  (доступ по JWT + шифрование бэкапа БД)? Зафиксировать решение в тикете.
- Логи/audit — не писать персональные данные детей в открытые логи
  (`System.out`/обычный логгер) без необходимости.

## 🚫 ЗАПРЕЩЁННЫЕ ПАТТЕРНЫ

> Стартовый список — пополнять реальными инцидентами по мере появления,
> по образцу numi (`SQLITE_BUSY`, multi-statement `tx.Exec` и т.д. — те
> списки родились из реальных багов, не выдуманы заранее).

- Hardcoded secret в коде (JWT secret, DB пароль, GitLab token) — всегда
  env var / application secrets, fail-fast при отсутствии.
- Изменение схемы БД через код при старте приложения (см. DEBT-1,
  `DatabaseFixConfig`) вместо нормальной SQL-миграции — не повторять этот
  паттерн для нового кода, даже если старый пример уже в проекте.
- `float`/`double` для денег, если/когда появится платёжный домен — всегда
  `BigDecimal`.
- Прямая конкатенация пользовательского ввода в SQL-строку (SQL injection) —
  всегда через `@Query` с параметрами или Spring Data derived queries.
- `System.out.println`/`printStackTrace` вместо нормального логгера
  (SLF4J/Logback) — особенно если может утечь персональная данные ребёнка
  в лог.
